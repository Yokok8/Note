# 异常处理（一）· 问题分析与两种方案

## 一、不做异常处理会怎样

### 异常是怎么"跑"上去的

    调用方向：Controller → Service → Mapper
    异常方向：Mapper → Service → Controller → 框架

| 层 | 出错后 |
|---|---|
| **Mapper** | 操作数据库时出错 → 异常往**上抛**（**谁调用 Mapper 就抛给谁**，所以抛给 Service） |
| **Service** | 自己没处理，异常继续往**上抛** → 抛给 Controller |
| **Controller** | 也没有任何异常处理 → 最终**抛给框架** |

### 抛给框架之后会怎样（课件原文）

> 最终抛给框架之后，框架就会返回一个 **JSON 格式的数据**，里面封装的就是错误的信息，但是框架返回的 JSON 格式的数据**并不符合我们的开发规范**。

框架默认返回长这样：

    {
      "timestamp": "2026-10-26T12:00:00.000+00:00",
      "status": 500,
      "error": "Internal Server Error",
      "path": "/emps/5"
    }

而我们整个项目约定的结构是：

    {
      "code": 0,
      "msg": "对不起，服务器异常，请联系管理员",
      "data": null
    }

### 到底哪里"不符合规范"

| 差异 | 后果 |
|---|---|
| **没有 `code` 字段** | 前端没法统一判断成功失败（我们靠 `code == 1`） |
| **没有 `msg` 字段** | 前端拿不到可以直接展示的中文提示 |
| **多了 timestamp / path / error** | 结构对不上，前端解析困难 |
| **暴露内部信息** | path 暴露接口路径，生产环境可能连带堆栈，属于安全隐患 |
| **HTTP 状态码是 500** | 前端 axios 拦截器常把 500 当成"系统崩溃"，直接弹通用错误页，用户看不到有效提示 |

**结论：必须把异常"截住"，换成我们自己的 `Result` 结构再返回。**&#8203;

## 二、方案一：在所有 Controller 方法里 try...catch

### 代码（图 2 完整重述）

    @GetMapping("/{id}")
    public Result getInfo(@PathVariable Integer id){
        try {
            log.info("根据id查询员工信息, id: {}", id);
            Emp emp = empService.getInfo(id);
            return Result.success(emp);
        } catch (Exception e) {
            return Result.error("对不起,服务器异常,请联累管理员");
        }
    }

    @PutMapping
    public Result update(@RequestBody Emp emp){
        try {
            log.info("修改员工信息, {}", emp);
            empService.update(emp);
            return Result.success();
        } catch (Exception e) {
            return Result.error("对不起,服务器异常,请联累管理员");
        }
    }

### 缺点：代码臃肿（课件明确标注"不推荐"）

| 问题 | 具体表现 |
|---|---|
| **重复代码多** | 每个方法都是同一套 `try { 业务 } catch (Exception e) { return Result.error(...) }` |
| **接口一多就失控** | 员工 8 个接口 + 部门 5 个接口 + 班级…… 每个都要包一遍 |
| **容易漏** | 新写的接口忘了加 try，就退回到"框架默认返回" |
| **业务代码被淹没** | 真正有意义的 2 行被 4 行模板包住，可读性差 |
| **改提示语要改 N 处** | 想把"请联系管理员"换成别的措辞，得全文替换 |

⚠️ 课件笔误：`请联累管理员` 应为 **`请联系管理员`**。

## 三、方案二：全局异常处理器（推荐）

### 好处（课件原文）

> **好处：简单、优雅（推荐）**&#8203;

### 原理（图 3）

    Controller 正常执行完毕 → 正常结果 → 直接返回前端

    Controller 执行出异常   → 交给「全局异常处理器」→ 异常结果 → 返回前端

- Controller 里**不用写一行 try...catch**，异常自然往上抛
- Spring 抛到最外层前会被**全局异常处理器**拦下，替换成规范的 `Result` 返回
- 三层架构本身一点不用改，只在旁边加一个类

### 代码

    @Slf4j
    @RestControllerAdvice
    public class GlobalExceptionHandler {

        @ExceptionHandler(Exception.class)
        public Result exceptionHandler(Exception e) {
            log.error("服务器异常：", e);        // 关键：异常必须记录，否则线上无从排查
            return Result.error("对不起，服务器异常，请联系管理员");
        }
    }

### 两个注解的含义

| 注解 | 含义 | 贴在哪 |
|---|---|---|
| **`@RestControllerAdvice`** | **全局异常处理器**的标记，等于 `@ControllerAdvice` + `@ResponseBody`，表示"这个类里的方法返回值直接序列化成 JSON" | **类上** |
| **`@ExceptionHandler(Exception.class)`** | 指定这个方法**能处理哪种异常** | **方法上** |

- `Exception.class` 是最宽的范围 → 所有异常（含 RuntimeException、SQLException 等）都能兜住
- `@ResponseBody` 那部分很关键：不加的话返回值会被当成"视图名"去找页面，直接 404 报错

### 加上之后完整链路

| 场景 | 原来的结果 | 现在的状态 |
|---|---|---|
| 查询成功 | `Result.success(emp)` | 不变 |
| MyBatis 抛 SQL 异常 | 框架默认 error JSON（500） | 被处理器接住 → `Result{code:0, msg:"..."}` |
| Service 抛 NPE | 同上 | 同上，且日志里有完整堆栈 |
| Controller 代码本身抛异常 | 同上 | 同上 |

**关键点：Controller 一行都不用改，之前写的 try 也可以全删。**&#8203;

## 四、两种方案对比

| | 方案一 try...catch | 方案二 全局异常处理器 |
|---|---|---|
| 代码量 | 每个方法 4 行模板 | **一个类 + 一个方法，全局通用** |
| 新增接口要做什么 | 记得加 try（容易漏） | **什么都不用做** |
| 返回结构 | 规范 | 规范 |
| 维护性 | 差（改措辞全文替换） | 好（只改一处） |
| 日志能否统一记录 | 各写各的 | **集中一处，好加告警** |
| 课件评价 | 代码臃肿（不推荐） | **简单、优雅（推荐）**&#8203; |

## 五、易错点

| 问题 | 后果 |
|---|---|
| 只写 `@ControllerAdvice` 漏了 `@ResponseBody` | 返回值被当成视图名解析，报 404 / 视图不存在 |
| `@ExceptionHandler` 捕获类型写太窄（如只写 `NullPointerException`） | 其他异常照样漏到框架 |
| **catch 里不记录日志** | 前端只看到"服务器异常"，后端一片空白，线上根本查不出原因 |
| 处理器类放在启动类**同包或子包之外** | 组件扫描不到，形同没写 |
| 用 `e.printStackTrace()` 打印 | 能看但没进日志文件，生产环境建议 `log.error(..., e)` |
| 加了全局处理器但 Controller 里还留着 try...catch | 能跑，但 try 里的 catch 会抢先处理掉，全局处理器收不到 |
| 多个 `@ExceptionHandler` 方法时以为按书写顺序执行 | 实际是**更精准（子类）的优先**，如自定义 `BusinessException` 会优于 `Exception` |

## 六、口诀

> **异常自下往上抛：Mapper → Service → Controller → 框架**
> **框架返回的 JSON 没有 code/msg，不符合规范，所以必须截住**
> **方案一 Controller 里挨个 try，代码臃肿不推荐**
> **方案二 `@RestControllerAdvice` + `@ExceptionHandler(Exception.class)`，一个类搞定全部接口**
> **处理器里一定要记日志，否则线上没法排查**
