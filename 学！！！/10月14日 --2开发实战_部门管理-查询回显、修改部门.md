# 根据 ID 查询部门（查询回显）
## 根据 ID 查询部门 · 思路分析

### 一、接口文档
| 项 | 值 |
|---|---|
| 请求路径 | **/depts/{id}** |
| 请求方式 | GET |
| 接口描述 | 该接口用于根据 ID 查询部门数据 |
| 参数格式 | **路径参数** |
| 参数 | id（number，必填） |
| 请求样例 | /depts/1　/depts/3 |

### 二、三层架构职责
| 层 | 职责 | 说明 |
|---|---|---|
| **Controller** | ① 接收请求参数（**路径参数**）② 调用 Service 层 ③ 响应结果 | 从 /depts/**1** 里取出 1 |
| **Service** | 调用 Mapper 接口方法 | 转发 id |
| **Mapper** | 执行查询 SQL | select * from dept where id = ? |

### 三、⭐ 重点：什么是"路径参数"
路径里的 `{id}` 就是一个**占位**，请求 `/depts/1` 时，`1` 就是那个 id。

| | 查询参数（老写法） | **路径参数（本次）**&#8203; |
|---|---|---|
| URL 长相 | /depts?id=8 | **/depts/1** |
| 路径定义 | /depts | **/depts/{id}** |
| 取值注解 | @RequestParam | **@PathVariable** |
| 例子 | 删除部门 | **根据 ID 查询** |

### 四、本项目三个接口的参数对照（整体感）
| 接口       | URL                | 参数类型     | 注解                |
| -------- | ------------------ | -------- | ----------------- |
| 查询全部部门   | GET /depts         | 无        | 无                 |
| 删除部门     | DELETE /depts?id=8 | 查询参数     | @RequestParam     |
| 根据 ID 查询 | GET /depts/1       | **路径参数** | **@PathVariable** |

记这个对照表，以后再看到新接口就知道该用哪个注解——**看 URL 里参数在 `?` 后还是拼在路径上**。

### 五、Mapper 层 SQL
    select * from dept where id = ?

- where id = ? 用占位符，对应注解里的 `#{id}`
- 查询结果只有一条 → 返回类型是 **Dept**（单个对象），不是 List

### 六、易错点
| 易错 | 说明 |
|---|---|
| 用 @RequestParam 取 /depts/1 | 接不到值，报 400 或 null |
| 注解路径忘写 {id} | /depts/1 匹配不上 → 404 |
| 返回类型写成 List\<Dept\> | 逻辑上只有一条，用 Dept 更准确 |
| 以为 /depts 和 /depts/{id} 冲突 | 不冲突，Spring 按路径精确匹配 |
| 查不到数据 | 返回 null，Controller 仍返回 code=1（要判断就自己加逻辑） |

### 七、口诀
- **路径参数 /depts/{id}，取值就用 @PathVariable**
- **问号后面用 RequestParam，斜杠后面用 PathVariable**
- **按 ID 查一条，返回的就是一个对象**

## Controller 接收路径参数（@PathVariable）

### 一、概念（课件原文）
**路径参数**：通过请求 URL 直接传递参数，使用 `{...}` 来标识该路径参数，需要使用 **@PathVariable** 获取路径参数。

    GET  /depts/1
          ↑ 这个 1 就是路径参数

### 二、两种写法

#### 写法一：形参名和路径变量名**不同** → 注解里必须写名字
    @GetMapping("/depts/{id}")
    public Result getInfo(@PathVariable("id") Integer deptId){
        System.out.println("根据ID查询部门数据： " + deptId);
        Dept dept = deptService.getInfo(deptId);
        return Result.success(dept);
    }

#### 写法二：形参名和路径变量名**相同** → 可以省略
    @GetMapping("/depts/{id}")
    public Result getInfo(@PathVariable Integer id){
        System.out.println("根据ID查询部门数据： " + id);
        Dept dept = deptService.getInfo(id);
        return Result.success(dept);
    }

两种写法效果**完全一样**，课件用红圈标出的三个位置就是关键点。

### 三、⭐ 三个名字的对应关系
| 位置 | 名字 | 规则 |
|---|---|---|
| 路径模板 | /depts/**{id}** | 叫什么，URL 就按什么传 |
| 注解 | @PathVariable( **“id”** &#8203;) | **必须和 {id} 里的名字一致** |
| 形参 | Integer **deptId** | **随便取**，靠注解绑定 |

- 前两个名字必须对上，否则接不到值
- 第三个名字自由，但 **一旦写成 id，注解里的名字就能省**

### 四、和 @RequestParam 的规则对照
| | @RequestParam | @PathVariable |
|---|---|---|
| 绑定对象 | 请求参数名 | 路径变量名 |
| 注解里写什么 | @RequestParam("id") | @PathVariable("id") |
| 什么时候能省 | 形参名 = 参数名 | 形参名 = 路径变量名 |
| 对应 URL | /depts?id=8 | /depts/1 |

**规则完全一样**：注解里的名字要和"外部的名字"对上，形参名对上就能省。

### 五、易错点
| 易错 | 说明 |
|---|---|
| 路径模板没写 {id} | /depts/1 匹配不到，404 |
| 注解写 @PathVariable("deptId") | 和 {id} 对不上，报错或接不到 |
| 漏写 @PathVariable | 参数为 null（Spring 不会自动绑定路径变量） |
| 类型写成 String 又当 int 用 | 建议直接写 Integer，Spring 自动转换 |
| 把 /depts 和 /depts/{id} 当成冲突 | 不冲突，Spring 能区分 |

### 六、口诀
- **路径参数靠 {} 占位，取值只用 @PathVariable**
- **{id} 和注解里的名字必须一致，形参名自由**
- **形参名一改对上，注解括号就能省**

## 根据 ID 查询部门 · 功能实现（三层完整代码）

### 一、DeptController
    @GetMapping("/depts/{id}")
    public Result getInfo(@PathVariable Integer id){
        System.out.println("根据ID查询部门数据： " + id);
        Dept dept = deptService.getInfo(id);
        return Result.success(dept);
    }
- `@GetMapping("/depts/{id}")`：路径里带占位符 {id}
- `@PathVariable Integer id`：**用的是写法二**（形参名 = 路径变量名，注解里不用写名字）
- `Result.success(dept)`：传**单个对象**，不是 List

### 二、DeptServiceImpl
    @Override
    public Dept getInfo(Integer id) {
        return deptMapper.getById(id);
    }
- 返回类型 **Dept**（一个对象）
- 注意：方法名叫 **getInfo**，但调的是 mapper 的 **getById**

### 三、DeptMapper
    @Select("select id, name, create_time, update_time from dept where id = #{id}")
    Dept getById(Integer id);
- 写全字段名（规范做法）
- `#{id}` 对应形参 id
- 返回类型 **Dept**

### 四、⚠️ 两个容易写混的地方
1. **方法名不一致**：Service 叫 `getInfo`，Mapper 叫 `getById`
   → 写代码时照着抄就行，别自己"统一"成一样的名字

2. **`#{}` 里写什么**，看参数类型：

| 参数类型 | 例子 | `#{}` 里写 | 实际 SQL |
|---|---|---|---|
| 简单类型 | Integer id | **形参名** → #{id} | where id = ? |
| 对象 | Dept dept | **属性名** → #{name} | values(?,?,?) |

### 五、返回值对照（三个查询的区别）
| 方法 | 返回类型 | 为什么 |
|---|---|---|
| findAll（查全部） | List\<Dept\> | 多条数据 |
| getById（按 ID 查） | **Dept** | 只有一条 |
| delete / add | void | 不需要返回 |

### 六、部门管理接口总览（截至目前）
| 功能 | 请求方式 | 路径 | 参数方式 | 注解 |
|---|---|---|---|---|
| 查询全部 | GET | /depts | 无 | 无 |
| 根据 ID 查询 | GET | /depts/1 | 路径参数 | @PathVariable |
| 新增 | POST | /depts | JSON 请求体 | @RequestBody |
| 删除 | DELETE | /depts?id=8 | 查询参数 | @RequestParam |
| 修改 | PUT | /depts | JSON 请求体 | @RequestBody（待学） |

### 七、易错点
| 易错 | 说明 |
|---|---|
| @GetMapping 写成了 "/depts" | 少了 {id}，/depts/1 匹配不上 → 404 |
| Service 方法名照 Mapper 改 | 改无所谓，但**接口和实现类要一致**，否则不叫重写 |
| 返回类型写成 List\<Dept\> | 查一条用 Dept 更准确 |
| 拿到 null 直接 Result.success(dept) | 前端会收到 data 为 null，code 仍是 1 |

### 八、口诀
- **路径 {id} + @PathVariable，形参同名可省注解**
- **Service 叫 getInfo、Mapper 叫 getById，跟课件走别自己统一**
- **简单类型写形参名，对象参数写属性名**

# 修改部门
## 修改部门 · 思路分析

### 一、接口文档
| 项 | 值 |
|---|---|
| 请求路径 | /depts |
| 请求方式 | **PUT** |
| 接口描述 | 该接口用于修改部门数据 |
| 参数格式 | **application/json** |
| 参数 | id（number）、name（string） |
| 请求样例 | { "id": 1, "name": "教研部" } |

对比新增：请求体**多了 id**，因为要告诉后端"改哪一行"。

### 二、三层架构职责
| 层 | 职责 | 说明 |
|---|---|---|
| **Controller** | ① 接收请求参数（json 格式）② 调用 Service 层 ③ 响应结果 | @RequestBody 接 Dept |
| **Service** | ① **补全基础属性** ② 调用 Mapper 接口方法 | ⭐ 本页核心 |
| **Mapper** | 执行 update SQL | 改 name 和时间 |

### 三、⭐ "补全基础属性"改了什么
| 功能 | 要补的属性 | 原因 |
|---|---|---|
| 新增部门 | createTime + updateTime | 新数据，两个时间都是现在 |
| **修改部门** | **只补 updateTime** | **创建时间不能改**，改了就不叫"创建时间"了 |

这是最容易看错的一点：**修改时绝不能动 createTime**。

### 四、Mapper 的 SQL
    update dept set name = ?, update_time = ? where id = ?

逐段拆解：
- `update dept` —— 改 dept 表
- `set name = ?, update_time = ?` —— **只改两个字段**（不是全表字段都写）
- `where id = ?` —— 定位改哪一行，**绝对不能漏**

注解写法对应：
    @Update("update dept set name = #{name}, update_time = #{updateTime} where id = #{id}")
    void update(Dept dept);
参数是 Dept 对象，所以 `#{}` 里写**属性名**。

### 五、新增 vs 修改 全对比
| | 新增 | 修改 |
|---|---|---|
| 请求方式 | POST | **PUT** |
| 请求体 | {name} | **{id, name}** |
| Service 补 | createTime + updateTime | **只补 updateTime** |
| SQL | insert ... values(?,?,?) | update ... set ?=? where id=? |
| 影响行数 | 1（新增一行） | 1（改一行，id 不存在则 0） |

### 六、业务流程串一遍（完整闭环）
1. 点"编辑"→ 调 **GET /depts/{id}** 把数据**回显**到表单
2. 改完提交 → 调 **PUT /depts**，请求体带 id + name
3. Service 补 updateTime → Mapper 执行 update

**回显用的就是"根据 ID 查询"那个接口** —— 这就是为什么那个接口要先学。

### 七、易错点
| 易错 | 说明 |
|---|---|
| 修改时把 createTime 也 set 了 | 创建时间被覆盖成当前时间，数据就错了 |
| 只 set name，忘了 updateTime | 修改时间不更新，失去意义 |
| SQL 漏 where id | **全表被改成同一个名字**，重大事故 |
| 忘写 @RequestBody | 接不到对象，全是 null |
| update 返回 void | 正常，不需要判断影响行数 |

### 八、口诀
- **PUT 改数据，请求体带 id + name**
- **新增补两个时间，修改只补 updateTime**
- **update 必须带 where id，set 只写要改的字段**

## 修改部门 · 功能实现（三层完整代码）

### 一、DeptController
    @PutMapping("/depts")
    public Result update(@RequestBody Dept dept){
        System.out.println("修改部门数据： " + dept);
        deptService.update(dept);
        return Result.success();
    }
- **@PutMapping**：对应 PUT 请求方式（新增用 @PostMapping，别写混）
- @RequestBody：接 JSON 请求体，转成 Dept 对象（里面带着 id 和 name）

### 二、DeptServiceImpl
    @Override
    public void update(Dept dept) {
        dept.setUpdateTime(LocalDateTime.now());
        deptMapper.update(dept);
    }
**只有一行 set** —— 这就是"修改部门只补 updateTime"：
- 不补 createTime（创建时间不改）
- 补 updateTime = 当前时间
- 然后才交给 Mapper

### 三、DeptMapper
    @Update("update dept set name = #{name}, update_time = #{updateTime} where id = #{id}")
    void update(Dept dept);
- **@Update**：专放修改 SQL 的注解
- `set name = #{name}, update_time = #{updateTime}` —— **只改这两个字段**
- `where id = #{id}` —— 用请求体里的 id 定位
- 参数是 Dept 对象 → `#{}` 里写**属性名**

### 四、新增 vs 修改 代码对照（一眼看出差别）
| | 新增 add | 修改 update |
|---|---|---|
| Controller 注解 | @PostMapping | **@PutMapping** |
| Service 补属性 | setCreateTime + setUpdateTime（**两行**） | setUpdateTime（**一行**） |
| Mapper 注解 | @Insert | **@Update** |
| SQL | insert ... values(?,?,?) | update ... set ?=? where id=? |

### 五、部门管理五接口总览（复习用）
| 功能 | 请求 | 接参注解 | Controller 返回 | Service/Mapper 返回 |
|---|---|---|---|---|
| 查询全部 | GET /depts | 无 | Result | List\<Dept\> |
| 根据 ID 查询 | GET /depts/{id} | @PathVariable | Result | Dept |
| 新增 | POST /depts | @RequestBody | Result | void |
| 修改 | PUT /depts | @RequestBody | Result | void |
| 删除 | DELETE /depts?id=8 | @RequestParam | Result | void |

记忆主线：**取 URL 上的参数用 Param / PathVariable，取请求体里的 JSON 用 RequestBody。**&#8203;

### 六、易错点
| 易错 | 说明 |
|---|---|
| @PutMapping 写成 @PostMapping | 前端 PUT 请求会 405 |
| Service 里顺手 setCreateTime | 创建时间被改掉，数据就错了 |
| SQL 漏 where id | **全表被改成同一个名字**，重大事故 |
| set 写在 mapper 调用之后 | update_time 还是 null |
| 忘记请求体里要有 id | where id = null，改不到任何数据 |

### 七、口诀
- **改数据用 PUT，@PutMapping 别写错**
- **修改只补 updateTime，创建时间不能动**
- **update 只 set 要改的字段，where id 必须带**

# @RequestMapping 抽取公共路径

## 一、问题：每个方法都在重复写 /depts
改进前：
    @RestController
    public class DeptController {

        @Autowired
        private DeptService deptService;

        @GetMapping("/depts")
        public Result list(){
            List<Dept> deptList = deptService.queryDeptList();
            return Result.success(deptList);
        }

        @DeleteMapping("/depts")
        public Result delete(Integer id){
            deptService.delete(id);
            return Result.success();
        }

        @PostMapping("/depts")
        public Result add(@RequestBody Dept dept){
            deptService.add(dept);
            return Result.success();
        }

        @GetMapping("/depts/{id}")
        public Result getInfo(@PathVariable Integer id){
            Dept dept = deptService.getInfo(id);
            return Result.success(dept);
        }
    }
四个方法各写一遍 /depts，**冗余**。

## 二、改进：把公共部分提到类上
改进后：
    @RequestMapping("/depts")
    @RestController
    public class DeptController {

        @Autowired
        private DeptService deptService;

        @GetMapping
        public Result list(){
            List<Dept> deptList = deptService.queryDeptList();
            return Result.success(deptList);
        }

        @DeleteMapping
        public Result delete(Integer id){
            deptService.delete(id);
            return Result.success();
        }

        @PostMapping
        public Result add(@RequestBody Dept dept){
            deptService.add(dept);
            return Result.success();
        }

        @GetMapping("/{id}")
        public Result getInfo(@PathVariable Integer id){
            Dept dept = deptService.getInfo(id);
            return Result.success(dept);
        }
    }
方法上只写**自己独有的那一段**，公共前缀提到类上。

## 三、⭐ 拼接规则（课件原文）
**一个完整的请求路径 = 类上的 @RequestMapping 的 value 属性 + 方法上的 @RequestMapping 的 value 属性**

| 方法 | 类上路径 | 方法上路径 | 实际完整路径 |
|---|---|---|---|
| list | /depts | （空） | **/depts** |
| delete | /depts | （空） | **/depts** |
| add | /depts | （空） | **/depts** |
| getInfo | /depts | /{id} | **/depts/{id}** |

注意：`@GetMapping` 后面**括号里什么都不写**是合法的——表示方法路径为空，完整路径就是类路径。

## 四、四种映射注解 + 类上 @RequestMapping 的完整组合
| 注解 | 请求方式 | 类路径 + 方法路径 = 完整 |
|---|---|---|
| @GetMapping | GET | /depts 或 /depts/{id} |
| @PostMapping | POST | /depts |
| @PutMapping | PUT | /depts |
| @DeleteMapping | DELETE | /depts |

## 五、易错点
| 易错 | 说明 |
|---|---|
| 类上写了 /depts，方法上又写 /depts | 变成 /depts/depts，**404** |
| 类上写了 /depts，方法上写 "/depts/{id}" | 变成 /depts/depts/{id}，错 |
| 方法上写成 "depts"（少斜杠） | Spring 会自动补，但规范写法还是加 / |
| 类上路径写成 depts（无斜杠） | 也能跑，但统一加 / 更清晰 |

## 六、口诀
- **公共路径提到类上，方法只写自己那段**
- **完整路径 = 类上 + 方法上，别重复写**
- **方法上括号可以为空，表示跟类路径一致**
