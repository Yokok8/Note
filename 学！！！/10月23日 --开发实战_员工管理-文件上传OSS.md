# 文件上传 - 阿里云 OSS（对象存储）

## 一、OSS 是什么（课件原文）

> **阿里云对象存储 OSS（Object Storage Service），是一款海量、安全、低成本、高可靠的云存储服务。使用 OSS，您可以通过网络随时存储和调用包括文本、图片、音频和视频等在内的各种文件。**&#8203;

拆开看四个卖点：

| 卖点 | 含义 | 对应本地存储的痛点 |
|---|---|---|
| **海量** | 容量几乎无上限，按量付费 | 本地磁盘 100G 存满就完 |
| **安全** | 多副本冗余、权限控制、防盗链 | 单机磁盘坏了数据就没了 |
| **低成本** | 只存不常用，单价比云盘低很多 | 自建还要买机器、做备份 |
| **高可靠** | 官方宣称 99.9999999999% 持久性 | 自己维护做不到 |

- 关键词：**对象存储** ≠ 文件系统，它没有"目录树"，所有文件扁平存在一个"桶"里，用 **Key** 标识

## 二、图里的架构（这页最该记住的）

    浏览器 ——① 文件上传——> 应用服务器 ——② 上传——> 阿里云 OSS

- **两次传输**，不是一次：
    1. 浏览器把文件提交给自己的服务器（还是上一节的 `MultipartFile`）
    2. 服务器拿到文件后，用 **OSS SDK** 再上传到云端
- 最终：**文件本体在 OSS，数据库里只存一个 URL 字符串**

### 和上一节本地存储的差别

|         | 本地存储（上一节）               | OSS             |
| ------- | ----------------------- | --------------- |
| 文件存哪    | `D:/images/` 服务器磁盘      | 阿里云机房           |
| 数据库存什么  | 文件名 / 相对路径              | **完整 URL**      |
| 访问方式    | 自己的服务器出流量转发             | 客户端**直接访问 OSS** |
| 多台服务器部署 | ❌ 文件只在一台的磁盘上，访问另一台就 404 | ✅ 都是同一个桶，天然共享   |
| 容量与备份   | 自己管                     | 云端自动冗余          |
| 成本      | 磁盘 + 带宽 + 运维            | 按存储量/流量付费       |

> 一句话：**本地存储是单机方案，OSS 是集群/分布式方案。**&#8203;


## 三、和上一节代码的对照（改动点在哪）

| 环节       | 本地存储版                            | OSS 版                                           |
| -------- | -------------------------------- | ----------------------------------------------- |
| 接收文件     | `MultipartFile file`             | **不变**                                          |
| 生成唯一文件名  | UUID + 扩展名                       | **不变**（OSS 上也要防重名覆盖）                            |
| 保存方式     | `file.transferTo(new File(...))` | `ossClient.putObject(bucket, key, inputStream)` |
| 返回值      | 文件名                              | **文件 URL**                                      |
| 数据库存的    | `1.jpg`                          | `https://bucket.xxx.aliyuncs.com/1.jpg`         |
| 大小限制 yml | 需要配                              | **仍然需要配**（服务器那一段还是 multipart）                   |

> 关键认知：**换成 OSS，只换"第 2 跳"的实现（transferTo → SDK 上传），前面收文件、生成文件名、大小限制全都照旧。**&#8203;

## 四、易错点

| 问题 | 后果 |
|---|---|
| 以为 OSS 是"云盘目录" | 它没有目录概念，Key 里的 `/` 只是名字的一部分，不是真目录 |
| AccessKey 写进前端 | 立刻泄露，别人可以随意删你的桶 |
| Bucket 名字随便起 | Bucket 名**全局唯一**，被别人占了就用不了 |
| 用了私有桶却直接拼 URL 访问 | 403，要生成签名 URL |
| 忘了设 Bucket 跨域（CORS） | 前端直传或前端直接展示时会失败 |
| 只上传不清理 | 删除员工时不删 OSS 文件 → 产生垃圾文件，持续计费 |
| 以为换了 OSS 就不用配 max-file-size | 第一跳仍是 multipart，照样会超限 |
| Endpoint 填成 `https://` 前缀 | SDK 要求只写域名不带协议，某些版本会报错 |

## 五、口诀

> **OSS = 海量、安全、低成本、高可靠的云端对象存储**
> **浏览器先给服务器，服务器再传 OSS，两次传输、文件不上自己磁盘**
> **数据库只存 URL，前端直接访问云端**
> **桶 Bucket、对象 Object、域名 Endpoint、密钥 AccessKey，四件套配齐就能用**
> **中转的上传会吃带宽，量大就换前端直传**

# 第三方服务通用思路 + 阿里云 OSS 使用步骤

## 一、这页讲的是"套路"而不是"知识点"

课件把接入任何第三方服务的做法抽成了三步，**跟具体是哪家云无关**：

| 阶段 | 干什么 | 一句话 |
|---|---|---|
| ① 准备工作 | 开通服务、拿凭证 | 让对方先认识你 |
| ② 参照官方 SDK 编写入门程序 | 跑通一个最小 demo | 证明"能连上" |
| ③ 集成使用 | 把 demo 逻辑搬进项目 | 真正用起来 |

- 先后顺序不能乱：**没准备就跑 demo 一定连不上；demo 没跑通就别急着往项目里塞**
- 这个套路对所有第三方服务都通用：短信、微信支付、地图 API、OCR、人脸识别，全都是这三步

## 二、SDK 是什么（课件原文）

> **SDK：Software Development Kit 的缩写，软件开发工具包，包括辅助软件开发的依赖（jar 包）、代码示例等，都可以叫做 SDK。**&#8203;

拆开理解：

| 组成 | 说明 | 例子里是什么 |
|---|---|---|
| **依赖（jar 包）**&#8203; | 别人封装好的工具类，你引进来就能调方法 | OSS 的 SDK jar，里面有 `OSSClient` |
| **代码示例** | 官方给的能直接跑的 demo | "快速入门"页面上那段 main 方法 |
| **配套文档** | API 说明、参数含义 | 官网开发指南 |

- 一句话：**SDK = 别人替你把复杂的 HTTP 签名、协议细节封好了，你只剩调方法**
- 对比一下：没有 SDK 时你要自己拼 HTTPS 请求、算签名、处理各种响应码；有 SDK 后就是 `client.putObject(...)` 一行

> ⚠️ 常见混淆：**SDK ≠ API**。API 是"能做什么"（接口说明），SDK 是"帮你调 API 的工具"。

## 三、OSS 使用七步（这页的主体）

    注册阿里云 → 充值 → 开通 OSS → 创建 bucket → 拿 AccessKey → 写入门程序 → 集成案例

| 步骤 | 做什么 | 关键说明 |
|---|---|---|
| 1 | **注册阿里云（实名认证）**&#8203; | 不实名很多云服务用不了 |
| 2 | **充值** | OSS 是按量付费的，余额为 0 会停服（新用户通常有免费额度/试用） |
| 3 | **开通对象存储服务（OSS）**&#8203; | 在控制台点开通，服务不会自动开通 |
| 4 | **创建 bucket** | 相当于"建一个存文件的桶" |
| 5 | **获取并配置 AccessKey（密钥）**&#8203; | 拿到 AccessKey ID + Secret，填进项目配置 |
| 6 | **参照官方 SDK 编写入门程序** | 引依赖、跑一个上传 demo |
| 7 | **案例集成 OSS** | 把 demo 改成 tlias 里的上传接口 |

### 和前一张图的对应

| 通用三步 | 对应 OSS 的哪几步 |
|---|---|
| 准备工作 | **第 1~5 步**（注册、充值、开通、建桶、拿密钥） |
| 参照官方 SDK 编写入门程序 | **第 6 步** |
| 集成使用 | **第 7 步** |

## 四、Bucket 是什么（课件原文）

> **Bucket：存储空间是用户用于存储对象（Object，就是文件）的容器，所有的对象都必须隶属于某个存储空间。**&#8203;

| 概念 | 关系 | 例子 |
|---|---|---|
| **Bucket（存储空间）**&#8203; | 容器，一个项目可以建一个 | `tlias-web2024` |
| **Object（对象）**&#8203; | 容器里的一个文件，**必须属于某个 Bucket** | `9f8e7d6c.jpg` |
| **Key（对象名）**&#8203; | Object 在桶里的唯一标识 | `9f8e7d6c.jpg` |

- Bucket 名字**全局唯一**（整个阿里云都不能重复），所以常加项目名前缀
- 建 Bucket 时还要选**地域**（如华北 2 北京）和**读写权限**（公共读 / 私有），选错后面要返工
- **地域选得离用户近**，访问速度更快；选错后不能改，只能重建

## 五、AccessKey 这一步最容易出事

| 要点 | 说明 |
|---|---|
| 一对密钥 | `AccessKey ID`（相当于用户名）+ `AccessKey Secret`（相当于密码） |
| 生成时只显示一次 | Secret 页面关掉就再也看不到，只能重新创建 |
| **绝不能提交到 Git** | 密钥泄露 = 别人能删你的桶、刷爆你的账单 |
| **绝不能发给前端** | 前端代码是公开的，等于直接泄露 |
| 推荐做法 | 用 **RAM 子账号**只授 OSS 权限，而不是主账号 AccessKey；配置放外置配置/环境变量 |

## 六、这七步在项目里最终落到什么

前五步是**在阿里云控制台点鼠标**，不写代码；只有后两步动代码。

| 阶段 | 产物 |
|---|---|
| 第 1~5 步 | 一个 Bucket 名、一个 Endpoint、一对 AccessKey |
| 第 6 步 | 一个能跑通的 main 方法（上传成功、打印 URL） |
| 第 7 步 | 项目 yml 里配 4 个参数 + 一个 `OssService`/`OssUtil`，Controller 里换成调它 |

配置将来大概长这样：

    aliyun:
      oss:
        endpoint: oss-cn-beijing.aliyuncs.com
        bucketName: tlias-web2024
        accessKeyId: LTAI5t******
        accessKeySecret: ******

## 七、易错点

| 问题 | 后果 |
|---|---|
| 跳过 demo 直接集成 | 出错时分不清是配置错还是业务代码错，排查翻倍 |
| 忘记实名认证 | 服务开通被拦 |
| 账户余额为 0 | 请求被拒绝，报 `AccessDenied` 之类 |
| Bucket 名用了大写/下划线 | 命名不合规，创建失败（只能小写字母、数字、短横线） |
| Endpoint 和 Bucket 地域不一致 | 上传报 `NoSuchBucket` 或超时 |
| Secret 提交到 Git | 密钥泄露，必须立刻在控制台禁用并重建 |
| 把 AccessKey 写进前端 | 任何人打开 F12 就能拿到，等于把桶送人 |
| 以为"开通 OSS"就等于"能用了" | 还得建 Bucket、拿密钥，缺一不可 |

## 八、口诀

> **通用三招：准备 → 跑官方 demo → 集成到项目**
> **OSS 七步：注册、充值、开通、建桶、拿密钥、写 demo、集成**
> **Bucket 是装 Object 的容器，Key 是文件在桶里的名字**
> **密钥只给后端、永不进 Git**

# 阿里云 OSS - 案例集成

## 一、两个步骤（图 1）

| 步骤  | 做什么                                 |
| --- | ----------------------------------- |
| ①   | **引入阿里云 OSS 文件上传工具类**（由官方的示例代码改造而来） |
| ②   | **上传文件接口开发**                        |

> 顺序很重要：**先有工具类，再写接口**。工具类是"能力"，接口只是"入口"。

## 二、UploadController 代码（图 1 完整重述）

    @Autowired
    private AliyunOSSOperator aliyunOSSOperator;

    /**
     * 文件上传
     */
    @PostMapping("/upload")
    public Result upload(MultipartFile file) throws Exception {
        log.info("文件上传:{}", file);
        String url = aliyunOSSOperator.upload(file.getBytes(), file.getOriginalFilename());
        return Result.success(url);
    }

### 逐行看

| 行 | 说明 |
|---|---|
| `@Autowired private AliyunOSSOperator` | 注入工具类，由 Spring 容器管理（工具类上要有 `@Component` 之类） |
| `@PostMapping("/upload")` | 路径 `/upload`，POST（上传必须 POST） |
| `MultipartFile file` | 接文件，参数名要和前端 `name="file"` 一致 |
| `file.getBytes()` | 拿到**文件的字节数组**（整个文件内容读进内存） |
| `file.getOriginalFilename()` | 拿到**原始文件名**，给工具类提取扩展名用 |
| `Result.success(url)` | **把 URL 返回给前端**，这是本接口的唯一产出 |

### 和上一节本地存储的对照

| | 本地存储 | OSS 集成后 |
|---|---|---|
| 拿文件内容 | `file.transferTo(new File(...))` | `file.getBytes()` |
| 存哪 | 服务器磁盘 | 云端 bucket |
| 谁拼路径 | Controller 里手写 `D:/images/` | **工具类内部**（含 Bucket、Endpoint、ObjectKey） |
| 返回值 | 文件名 | **完整 URL** |

## 三、AliyunOSSOperator 内部做了什么（课件没贴，但必须知道）

工具类虽然没给代码，但它的职责就四件事：

| 内部步骤 | 对应代码（官方示例改造后） |
|---|---|
| ① 生成唯一文件名 | 复用上一节：`UUID` 去横线 + 原扩展名 |
| ② 创建 OSS 客户端 | `new OSSClientBuilder().build(endpoint, accessKeyId, accessKeySecret)` |
| ③ 上传对象 | `client.putObject(bucketName, objectKey, new ByteArrayInputStream(bytes))` |
| ④ 拼出访问 URL | `https://{bucketName}.{endpoint}/{objectKey}` 并 return |

配置项来自 `application.yml`：

    aliyun:
      oss:
        endpoint: oss-cn-beijing.aliyuncs.com
        bucketName: tlias-web2024
        accessKeyId: LTAI5t******
        accessKeySecret: ******

- 工具类用 `@Value("${aliyun.oss.endpoint}")` 之类注入，**不要写死在代码里**
- `putObject` 第三个参数需要 `InputStream`，所以要把 `byte[]` 包一层 `ByteArrayInputStream`

## 四、业务流程（图 2）

### UploadController 的三个职责

| 序号 | 职责 |
|---|---|
| 1 | **接收上传的图片** |
| 2 | **将图片存储起来（OSS）**&#8203; |
| 3 | **返回图片访问的 URL** |

### 真正的交互是"两步走"

| 步骤 | 谁 | 干什么 |
|---|---|---|
| ① | 前端 | 用户在新增员工页选图 → 调 `/upload` |
| ② | 后端 | 存到 OSS，返回 URL 字符串 |
| ③ | 前端 | **把 URL 回填到表单的 `image` 字段**（同时显示预览图） |
| ④ | 前端 | 点"提交"→ 调 `save` 接口，请求体里 `image` 就是那个 URL |
| ⑤ | 后端 | `empMapper.insert(emp)` → **emp 表的 image 列存的是 URL** |

图 2 里下方那段代码就是第 ④ 步走的接口：

    /**
     * 添加员工
     */
    @PostMapping
    public Result save(@RequestBody Emp emp) {
        log.info("请求参数emp: {}", emp);
        empService.save(emp);
        return Result.success();
    }

### 为什么必须拆成两个接口

- **图片选完就能立刻上传**：用户选完图马上看到预览，不用等点提交
- 表单可能有多个附件，各自独立上传
- 图片上传成功但用户放弃填表单 → 图片已在 OSS（有少量垃圾文件，可后续清理）
- 如果合成一个接口，`MultipartFile` + JSON 混在一起传会很别扭

## 五、页面上的两个校验提示（图 2 里的小字）

> 图片大小不能超过 2M；只能上传 jpg 格式的图片

| 校验 | 前端 | 后端（必须也做） |
|---|---|---|
| 大小 ≤ 2MB | `file.size` 比较后提示 | `file.getSize()` 判断，超了抛异常 |
| 仅 jpg | `accept=".jpg"` + 扩展名判断 | 校验 `getOriginalFilename()` 后缀 或 `getContentType()` |

- ⚠️ **前端校验只是体验，后端校验才是安全**。前端能绕过（改 JS、直接 Postman 调接口）
- 后端校验失败要返回明确的错误信息，而不是 500

## 六、易错点

| 问题 | 后果 |
|---|---|
| 工具类没加 `@Component` 就 `@Autowired` | 启动报 `NoSuchBeanDefinitionException` |
| 用 `file.getBytes()` 传大文件 | 整个文件读进内存，100MB 视频会 OOM；大文件要改用 `getInputStream()` |
| 拼 URL 时 Bucket 和 Endpoint 顺序搞反 | URL 打不开（正确是 `{bucket}.{endpoint}`） |
| 忘了给对象名加扩展名 | 浏览器识别不了文件类型，图片显示不出来 |
| 把 AccessKey 写死在工具类 | 泄露风险，且换环境要改代码 |
| 只做前端大小校验 | 用 Postman 直接调接口就能绕过传超限文件 |
| 上传成功就以为员工能显示了 | 还需要 `save` 把 URL 存进 emp 表的 image 列 |
| `upload` 方法没写 `throws Exception` | 编译不过（SDK 会抛受检异常） |

## 七、口诀

> **先引工具类，再写接口**
> **Controller 三句：收文件、调工具、返 URL**
> **工具类收 bytes + 原文件名，内部改名、putObject、拼 URL**
> **上传和保存是两个接口：先拿 URL 回填表单，再提交入库**
> **大小和格式，前端提示、后端把关**

# 优化1：参数配置化（@Value）

## 一、思考题：参数写在 Java 代码里有什么问题

图 1 的代码（三行被红线划掉）：

    @Component
    public class AliyunOSSOperator {

        private String endpoint = "https://oss-cn-beijing.aliyuncs.com";
        private String bucketName = "java-ai";
        private String region = "cn-beijing";

        public String upload(byte[] content, String originalFilename) throws Exception {
            // 从环境变量中获取访问凭证。运行本代码示例之前，请确保已设置环境变量
            // OSS_ACCESS_KEY_ID 和 OSS_ACCESS_KEY_SECRET
            EnvironmentVariableCredentialsProvider credentialsProvider =
                    CredentialsProviderFactory.newEnvironmentVariableCredentialsProvider();
            // ...
        }
    }

### 四大问题

| 问题 | 具体表现 |
|---|---|
| **① 改配置就要改代码** | 换个 bucket 名 → 改 java → 重新编译 → 打包 → 重启服务；运维根本没法自己改 |
| **② 多环境无法共存** | 开发、测试、生产用的 endpoint/bucket 都不一样，写死就只能一套代码维护多个分支 |
| **③ 敏感信息进仓库** | AccessKey、密码写进 java 会被提交到 Git，泄露风险 + 无法审计谁看过 |
| **④ 错误发现得太晚** | 字符串拼错（如 `bukcet`）编译期没问题，只有运行时才炸 |

> 一句话：**凡是"会变的值"和"敏感的值"，都不该出现在 java 源码里。**&#8203;

### 顺带注意凭证的处理

图里凭证没用字符串，而是：

    EnvironmentVariableCredentialsProvider credentialsProvider =
            CredentialsProviderFactory.newEnvironmentVariableCredentialsProvider();

- 意思是**从操作系统环境变量读** `OSS_ACCESS_KEY_ID` 和 `OSS_ACCESS_KEY_SECRET`
- 这是官方示例的推荐做法：**账号密码不进代码、不进 Git、不进 yml**
- 所以在工具类里只配置 endpoint / bucketName / region 这三个"不敏感但会变"的参数

## 二、参数配置化的定义（课件原文）

> **上参数配置化：指将一些需要灵活变化的参数，配置在配置文件中，然后通过 @Value 注解来注入外部配置的属性。**&#8203;

只记三句话：

| 要素 | 内容 |
|---|---|
| 配置写到哪 | **配置文件**（application.yml） |
| 怎么取出来 | **`@Value` 注解** |
| 语法 | **`@Value("${key}")`** |

## 三、application.yml 配置

    aliyun:
      oss:
        endpoint: https://oss-cn-beijing.aliyuncs.com
        bucketName: java-ai
        region: cn-beijing

- yml 靠**缩进**表示层级：`aliyun` → `oss` → 三个子项
- 缩进**只能用空格**，用 Tab 会解析报错
- 冒号后面**必须有空格**（`bucketName: java-ai`，不是 `bucketName:java-ai`）

## 四、Java 里用 @Value 注入

    @Component
    public class AliyunOSSOperator {

        @Value("${aliyun.oss.endpoint}")
        private String endpoint;

        @Value("${aliyun.oss.bucketName}")
        private String bucketName;

        @Value("${aliyun.oss.region}")
        private String region;
    }

### 关键规则：key 用「点」代替「缩进」

| yml 里的层级 | @Value 里写成 |
|---|---|
| `aliyun` → `oss` → `endpoint` | `aliyun.oss.endpoint` |
| `aliyun` → `oss` → `bucketName` | `aliyun.oss.bucketName` |

- **${} 里必须是完整路径**，少一层（如 `@Value("${endpoint}")`）取不到
- 属性名不必和 key 一样（`@Value("${aliyun.oss.bucketName}") private String bucket;` 也能跑），但**建议同名**，方便对照
- `@Value` 贴在**字段**上（也可贴构造/方法参数），字段不能是 `static`，也不能是 `final`

## 五、改造前后对比

| | 硬编码 | 配置化 |
|---|---|---|
| 值写在哪 | java 源码里 | application.yml |
| 改 bucket 名 | 改代码 + 重打包 + 重启 | **改 yml + 重启**（打包后也能改外置配置） |
| 换环境 | 改代码分支 | 换一份 yml / 切 profile |
| 敏感值 | 易进 Git | 可与代码分离 |
| 运维能否操作 | ❌ | ✅ |

- 注意：改了 yml 仍然要**重启**（除非配了 `spring-boot-devtools` 或配置中心热更新）

## 六、易错点

| 问题 | 报错 / 现象 |
|---|---|
| key 拼错（如 `aliyun.os.endpoint`） | 启动报 `IllegalArgumentException: Could not resolve placeholder 'aliyun.os.endpoint'` |
| 少了某一层路径 | 同上，占位符无法解析 |
| `${}` 写成 `#{}` | `#{}` 是 SpEL 表达式，取不到配置值 |
| yml 用 Tab 缩进 | `while scanning for the next token found character '\t'` |
| 冒号后没空格 | 值会被当成 key 的一部分，解析异常 |
| 把 AccessKey 写进 yml 并提交 Git | 仍然会泄露，应放环境变量/配置中心 |
| `@Value` 标在 `static` 字段上 | 注入后仍为 null |
| 类上忘了 `@Component` | 对象不由 Spring 管理，`@Value` 不生效 |

## 七、口诀

> **会变的、敏感的，都不许写在 java 里**
> **yml 缩进三层，@Value 点号三段**
> **`@Value("${aliyun.oss.endpoint}")` 一个字段一个注解**
> **改值不用改代码，换环境只换文件**

# 优化2：@ConfigurationProperties（批量绑定配置）

## 一、问题分析（图 1）

> **使用 @Value 注解注入配置文件的配置项，如果配置项多，注入繁琐，不便于维护管理和复用。**&#8203;

图里把 `endpoint`、`bucketName` 又重复画了两遍，就是在演示这件事：**每多一个类用到配置，就要把这三个字段连注解再写一遍。**&#8203;

拆成三个问题看：

| 问题 | 具体表现 |
|---|---|
| **注入繁琐** | 1 个字段 = 1 个 `@Value` + 1 个字段声明，3 个参数就是 6 行 |
| **不便于维护** | yml 里 key 改名 → 每个类里的 `@Value("${...}")` 都要跟着改 |
| **不便于复用** | 这段字段声明在类之间没法复用，只能复制粘贴 |

- 一个类时感觉还行，**类一多就崩**（OSS 工具类、导出工具、其他服务可能都要这些配置）

## 二、解决方案：建一个属性类

    @Data
    @Component
    @ConfigurationProperties(prefix = "aliyun.oss")
    public class AliyunOSSProperties {
        private String endpoint;
        private String bucketName;
        private String region;
    }

### 三个注解各自干什么（缺一不可）

| 注解 | 作用 | 不加会怎样 |
|---|---|---|
| **`@Data`** | Lombok 生成 getter/setter/toString | 没有 setter → **Spring 没法赋值，字段全 null** |
| **`@Component`** | 交给 Spring，注册成一个 Bean | 不是 Bean，`@Autowired` 注入不进来 |
| **`@ConfigurationProperties(prefix = "aliyun.oss")`** | 把 `aliyun.oss` 下的 key **按名字批量绑定**到同名字段 | 不绑定，字段还是 null |

> 重点理解 `@Data`：很多人以为只是为了省 getter，其实 **setter 是它必需的原因**——`@ConfigurationProperties` 是靠反射调 setter 把 yml 的值写进对象的。

### prefix 和字段怎么对应

yml：

    aliyun:
      oss:
        endpoint: https://oss-cn-beijing.aliyuncs.com
        bucketName: java-ai
        region: cn-beijing

对应关系：

| 位置 | 写法 |
|---|---|
| **prefix** | `aliyun.oss`（**只写到 oss，不含子项**） |
| **字段名** | `endpoint` / `bucketName` / `region`（= 子 key 名，必须一致） |

- prefix 多写一层（`aliyun.oss.endpoint`）→ 绑定不到任何东西，字段全 null
- prefix 少写一层（`aliyun`）→ 它会把 `oss` 当成一个属性去找，同样绑不上

## 三、使用处：注入这个 Bean 就能用

    @Component
    public class AliyunOSSOperator {

        @Autowired
        private AliyunOSSProperties aliyunOSSProperties;

        public String upload(byte[] content, String originalFilename) throws Exception {
            String endpoint = aliyunOSSProperties.getEndpoint();
            String bucketName = aliyunOSSProperties.getBucketName();
            // ...
        }
    }

- 其他类想用配置：**只需 `@Autowired` 这一个对象**，再加一行 `getXxx()`
- 配置项从 3 个变成 10 个，引用它的类也**一行都不用改**
- yml 里 key 改名 → 只改属性类这一处

## 四、@Value vs @ConfigurationProperties

| | `@Value` | `@ConfigurationProperties` |
|---|---|---|
| 注入粒度 | **一个字段一个注解** | **一个前缀批量绑定** |
| 代码量（3 个参数） | 6 行 | 属性类 3 行 + 引用处 1 行 |
| 多处复用 | ❌ 每处重写 | ✅ 注入同一个 Bean |
| key 改名的维护 | 要改每一处 | 只改属性类 |
| **key 拼错时** | **启动直接报错**（`Could not resolve placeholder`） | **不报错，值为 null**（静默失败） |
| 松散绑定 | 不支持（必须一模一样） | 支持 `bucket-name` / `bucketName` / `BUCKET_NAME` |
| 适合场景 | 参数少（1~2 个）、临时取一个值 | **参数多、成组、多处使用（推荐）**&#8203; |

> 最后那个差异很关键：`@Value` 是"错得响"，`@ConfigurationProperties` 是"错得静"。用后者时要**从代码里真的读出值来验证一遍**，别只看启动成功。

## 五、两种注解可以共存

实际项目里常见混用：

    @Value("${server.port}")
    private Integer port;                     // 单个零散值，@Value 更省事

    @Autowired
    private AliyunOSSProperties ossProperties; // 成组配置，用属性类

- 不用纠结"必须选一个"，按数量判断就好

## 六、易错点

| 问题 | 后果 |
|---|---|
| 只写 `@Data` 漏了 `@Component` | 属性类不是 Bean，注入失败（`NoSuchBeanDefinitionException`） |
| 漏了 `@Data`（也没手写 setter） | 所有字段 null，上传时报 endpoint 为空 |
| `prefix` 写到最末一层（`aliyun.oss.endpoint`） | 绑定不到，全 null |
| 字段名和 yml 的 key 不一致 | **不报错，值为 null**，最坑 |
| 字段加了 `final` | 无法调 setter，绑定失败 |
| 属性类扫不到 | 启动类同包或子包之外需要 `@EnableConfigurationProperties` 或显式 `@ComponentScan` |
| 以为改了 yml 立刻生效 | 需要重启（除非用配置中心/devtools） |

## 七、口诀

> **`@Value` 一个字段一个注解，参数一多就繁琐**
> **`@ConfigurationProperties` + prefix，字段名对上就批量绑**
> **三注解齐活：`@Data` 给 setter、`@Component` 给 Bean、prefix 给范围**
> **prefix 写到组名为止，字段名一字不差；错了不报错，值是 null**
