# 一对一（特殊的一对多，多了unique）

## 一、案例
**用户 与 身份证信息** 的关系：一个用户只有一张身份证，一张身份证只属于一个用户。

## 二、关系说明（课件原文）
一对一关系，**多用于单表拆分**：
将一张表的基础字段放在一张表中，其他字段放在另一张表中，**以提升操作效率**。

为什么要拆：
- 一张大表字段太多，**常用字段和不常用字段混在一起**
- 查常用信息时也被迫扫描那些又长又大的字段（如身份证号、签发机关）
- 拆开后：**主表只放常用字段、查得快；副表按需关联**

## 三、⭐ 实现方式（课件红字，背下来）
> **在任意一方加入外键，关联另外一方的主键，并且设置外键为唯一的（UNIQUE）**&#8203;

三个关键词：**任意一方** + **关联对方主键** + **UNIQUE 唯一**

## 四、两张表长什么样（照图）

### tb_user 用户基本信息表
| id（主键） | name | gender | phone | degree |
|---|---|---|---|---|
| 1 | 白眉鹰王 | 1 | 18812340001 | 初中 |
| 2 | 青翼蝠王 | 1 | 18812340002 | 大专 |
| 3 | 金毛狮王 | 1 | 18812340003 | 初中 |
| 4 | 紫衫龙王 | 2 | 18812340004 | 硕士 |

### tb_user_card 用户身份信息表
| id | name | birthday | idcard | issued | expire_begin | expire_end | **user_id** |
|---|---|---|---|---|---|---|---|
| 1 | 汉 | 1960-11-06 | 100000100000000001 | 朝阳区公安局 | 2000-06-10 | null | **1** |
| 2 | 汉 | 1971-11-06 | 100000100000000002 | 静安区分局 | 2005-06-10 | 2025-06-10 | **2** |
| 3 | 汉 | 1963-11-06 | 100000100000000003 | 昌平区公安局 | 2006-06-10 | null | **3** |
| 4 | 回 | 1980-11-06 | 100000100000000004 | 海淀区公安局 | 2008-06-10 | 2028-06-10 | **4** |

关联：tb_user.**id** ←→ tb_user_card.**user_id**
本例是把外键加在了**身份信息表**这一方（任意一方都可以）。

## 五、⭐ 为什么外键必须加 UNIQUE
| 加 UNIQUE | 不加 UNIQUE |
|---|---|
| 一个 user_id 只能出现一次 | 同一个 user_id 可以出现多次 |
| → **一对一** | → **退化成一対多**（一个用户多张身份证，不合理） |

**一句话：一对多和一对一的唯一区别，就在外键有没有唯一约束。**&#8203;

## 六、三种关系对比（串起来记）
| 关系 | 外键加在哪 | 外键是否唯一 |
|---|---|---|
| 一对多 | **多的一方** | 不唯一（可重复） |
| **一对一** | **任意一方** | **必须 UNIQUE** |
| 多对多 | 不在原表，用中间表 | — |

## 七、易错点
| 易错 | 说明 |
|---|---|
| 忘了设 UNIQUE | 直接变成一对多，逻辑就错了 |
| 以为只能加在某一边 | **任意一方**都行，看业务哪个方便 |
| 主表副表搞反 | 基础字段的是主表（tb_user），扩展字段的是副表 |
| 理解成"所有表都该拆" | 只有字段多、冷热明显时才拆，拆多了反而要多表关联 |

## 八、口诀
- **一对一为拆分，基础字段留主表，其余搬副表**
- **任意一方加外键，关联对方主键，外加 UNIQUE**
- **忘了 UNIQUE 就变一对多**

# 创建一对一 · SQL 完整示例

## 一、两张表（用户 + 身份证，单表拆分）
    -- ① 主表：用户基本信息（常用字段）
    create table tb_user(
        id int unsigned primary key auto_increment comment 'ID',
        name varchar(10) not null comment '姓名',
        gender tinyint unsigned not null comment '性别, 1 男, 2 女',
        phone char(11) not null comment '手机号',
        degree varchar(10) comment '学历'
    ) comment '用户基本信息表';

    -- ② 副表：用户身份信息（不常用/长字段）—— 关键：user_id 加了 UNIQUE
    create table tb_user_card(
        id int unsigned primary key auto_increment comment 'ID',
        nationality varchar(10) not null comment '民族',
        birthday date not null comment '生日',
        idcard char(18) not null comment '身份证号',
        issued varchar(20) not null comment '签发机关',
        expire_begin date comment '有效开始日期',
        expire_end date comment '有效截至日期',
        user_id int unsigned not null unique comment '用户ID, 唯一',
        create_time datetime not null comment '创建时间',
        update_time datetime not null comment '修改时间'
    ) comment '用户身份信息表';

**核心就一个词：UNIQUE。**&#8203; 外键字段后面加 `unique`，一对一就成了。

## 二、③ 建立关联（三种写法）

### 写法 A：建完表后加外键（学习阶段用）
    alter table tb_user_card add constraint fk_card_user foreign key (user_id) references tb_user(id);

### 写法 B：建表时连外键一起写（效果同上）
    create table tb_user_card(
        id int unsigned primary key auto_increment comment 'ID',
        ...
        user_id int unsigned not null comment '用户ID',
        unique(user_id),
        constraint fk_card_user foreign key (user_id) references tb_user(id),
        create_time datetime not null comment '创建时间',
        update_time datetime not null comment '修改时间'
    ) comment '用户身份信息表';

### 写法 C：只加 UNIQUE 不加 foreign key（企业做法 = 逻辑外键）
    -- 就上面那两张建表语句，保留 unique，不写 alter
    -- 关联交给 Service 层代码保证（推荐）

## 三、⭐ 和一对多 SQL 的唯一差别
| 关系 | 外键字段定义 | 能不能重复 |
|---|---|---|
| 一对多 | dept_id int unsigned | **可以重复** |
| **一对一** | user_id int unsigned **unique** | **不能重复** |

**记住：把一对多的 SQL 复制过来，在外键字段后加个 unique，就变成一对一了。**&#8203;
不加 unique → 同一个 user_id 能出现多次 → 直接退化成一対多。

## 四、补充操作
    -- 看外键名 / 删外键
    show create table tb_user_card;
    alter table tb_user_card drop foreign key fk_card_user;

    -- 插数据（先主表，再副表）
    insert into tb_user(name, gender, phone, degree) values('白眉鹰王', 1, '18812340001', '初中');
    insert into tb_user_card(nationality, birthday, idcard, issued, expire_begin, user_id, create_time, update_time)
    values('汉', '1960-11-06', '100000100000000001', '朝阳区公安局', '2000-06-10', 1, now(), now());

    -- 查用户 + 身份证
    select u.name, c.idcard from tb_user u left join tb_user_card c on u.id = c.user_id;

    -- 验证唯一性：再插一条 user_id=1 的会报错
    insert into tb_user_card(nationality, birthday, idcard, issued, user_id, create_time, update_time)
    values('汉', '1970-01-01', '100000100000000009', '某局', 1, now(), now());   -- ERROR: Duplicate entry

## 五、易错
| 易错 | 说明 |
|---|---|
| **忘了写 unique** | 最常见！加完外键但没唯一 → 逻辑上变成一对多 |
| 类型不一致 | user_id 必须和 tb_user.id 同为 int unsigned |
| 顺序反了 | 先建主表再建副表，否则外键引用不到 |
| 以为外键只能加在副表 | **任意一方都行**，加在主表也合法（但本例加在副表更自然） |
| 副表字段写 not null 又没给值 | user_id 建议 not null，插入时必须给 |

## 六、口诀
- **一对一的 SQL = 一对多的 SQL + UNIQUE**
- **任意一方加外键，关联对方主键，外加唯一约束**
- **没 unique 就是一对多，有 unique 才是一对一**

# 多对多（创建第三张表进行关联）

## 一、案例与关系
- **案例**：学生 与 课程 的关系
- **关系**：一个学生可以选修多门课程，一门课程也可以供多个学生选择

## 二、⭐ 实现方式
> **建立第三张中间表，中间表至少包含两个外键，分别关联两方主键。**&#8203;

三个要点：**第三张表** + **至少两个外键** + **分别关联两方主键**

## 三、三张表长什么样（照图）

### 学生表 tb_student（N）
| id（主键） | name | no |
|---|---|---|
| 1 | 黛绮丝 | 2000100101 |
| 2 | 谢逊 | 2000100102 |
| 3 | 殷天正 | 2000100103 |
| 4 | 韦一笑 | 2000100104 |

### 学生课程关系表 tb_student_course（中间表）
| id | studentid（外键） | courseid（外键） |
|---|---|---|
| 1 | 1 | 1 |
| 2 | 1 | 2 |
| 3 | 1 | 3 |
| 4 | 2 | 1 |
| 5 | 2 | 4 |

### 课程表 tb_course（N）
| id（主键） | name |
|---|---|
| 1 | Java |
| 2 | PHP |
| 3 | MySQL |
| 4 | Hadoop |

关联：tb_student.**id** → tb_student_course.**studentid**；tb_course.**id** → tb_student_course.**courseid**

## 四、中间表怎么读
**中间表每一行 = 一条"谁选了什么课"的记录**：
- 学生 1（黛绮丝）→ 选了 1 Java、2 PHP、3 MySQL（三行）
- 学生 2（谢逊）→ 选了 1 Java、4 Hadoop（两行）
- 课程 1（Java）→ 被学生 1 和学生 2 都选了（两行）

→ **studentid 会重复、courseid 也会重复，但两列组合起来不重复**，这就是多对多。

## 五、建表 SQL（配套给你）
    -- 学生表
    create table tb_student(
        id int unsigned primary key auto_increment comment 'ID',
        name varchar(10) not null comment '姓名',
        no char(10) not null comment '学号'
    ) comment '学生表';

    -- 课程表
    create table tb_course(
        id int unsigned primary key auto_increment comment 'ID',
        name varchar(20) not null comment '课程名称'
    ) comment '课程表';

    -- 中间表：两个外键 + 联合唯一
    create table tb_student_course(
        id int unsigned primary key auto_increment comment 'ID',
        studentid int unsigned not null comment '学生ID',
        courseid int unsigned not null comment '课程ID',
        unique(studentid, courseid) comment '同一个学生不能重复选同一门课'
    ) comment '学生课程关系表';

> 中间表**不需要** student_name、course_name 这类字段 —— 名字去两张主表里查，中间表只存 id 关系。

## 六、三种关系总对比（收尾）
| 关系 | 表数量 | 外键在哪 | 关键点 |
|---|---|---|---|
| 一对多 | 2 张 | 多的一方 | 外键可重复 |
| 一对一 | 2 张 | 任意一方 | 外键必须 **UNIQUE** |
| **多对多** | **3 张** | **中间表里两个** | **中间表 + 联合唯一** |

## 七、易错点
| 易错 | 说明 |
|---|---|
| 只在一边加外键 | 多对多必须**两张主表都关联**，缺一边就退化成一对多 |
| 中间表带业务字段 | 中间表只存两个 id + 自己的 id，不要塞姓名 |
| 忘了联合唯一约束 | 同一个学生同一门课能被插入两次，数据重复 |
| 把中间表当主表用 | 它只是关系表，查数据要连三张表 |

## 八、口诀
- **多对多要第三张表，两个外键分别连两方主键**
- **中间表一行 = 一条关系记录**
- **两列都重复但组合唯一 → 这就是多对多**
