# ══════ JWT 令牌 —— 介绍 ══════

## 一、核心速记（图上三条定义）

    全称：JSON Web Token    官网：https://jwt.io/
    定义：一种简洁的、自包含的格式，
         用于在通信双方以 json 数据格式安全的传输信息
    组成：三段，用 .（点）连接 →  Header . Payload . Signature

  · 「简洁」= 就是一串字符串，塞进请求头就能传，不需要额外存储结构
  · 「自包含」= **信息全在令牌自己身上**，服务器拿到令牌就知道你是谁，不用去查内存/数据库
  · 「安全的传输」= 靠第三段数字签名保证「没被改过」，而不是靠把内容藏起来

## 二、三段结构详解（图上原文 + 补充）

| 段位 | 名称 | 记录什么 | 图上示例 | 编码方式 |
| --- | --- | --- | --- | --- |
| 第一部分 | Header（头） | 令牌类型、签名算法 | {"alg":"HS256","type":"JWT"} | Base64 |
| 第二部分 | Payload（有效载荷） | 自定义信息 + 默认信息 | {"id":"1","username":"Tom"} | Base64 |
| 第三部分 | Signature（签名） | 防篡改、保安全 | Sf1KxwRJSMeKKF2QT4fwpMeJf... | 算法计算，不可解 |

### ① Header（头）

    {"alg": "HS256", "type": "JWT"}

  · alg = 签名算法，HS256 是 HMAC-SHA256（对称加密：**签发和校验用同一个密钥**）
  · 另一种常见 alg 是 RS256（非对称：私钥签、公钥验，适合微服务/多系统）
  · 课件笔误：标准 RFC 7519 里这个字段叫  **“typ”** &#8203;，不是 "type"；标准值 typ=JWT、alg=HS256

### ② Payload（有效载荷）

    {"name": "Tom", "iat": 1516239022}          // iat = issued at 签发时间（秒级时间戳）
    {"id": "1", "username": "Tom"}              // 课件正文给的自定义信息示例

  · 自定义信息：id、username、name 这类「服务器识别用户身份」的数据
  · 默认信息（JWT 预留声明）：
      iat —— 签发时间
      exp —— 过期时间（后端 JWT 过期失效全靠它）
      sub —— 主题、nbf —— 生效时间
  · **iat 是秒**，Java 里 `System.currentTimeMillis()` 是**毫秒**，得除以 1000
  · ⚠️ 关键认知：Payload 只是 Base64，**不是加密**，谁都能解出明文
      → 绝不能放 password、手机号、身份证

### ③ Signature（签名）

    数字签名(header.payload, secret)

  · 算法：拿「Header 的 Base64 + "." + Payload 的 Base64」，再用**指定密钥**跑 HS256，得到签名
  · 作用：防篡改 —— 改一个字符，服务端重算签名就对不上 → 直接拒绝
  · 「确保安全性」这三个字指的就是防篡改，不是防偷看

## 三、图下那行真实令牌对照着看

    eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9  .  eyJ...JTdC...  . Sf1KxwRJSMeKKF2QT4fwpMeJf...
    └────── 绿：Header 的 Base64 ──────┘    └─ 紫：Payload ─┘    └──── 红：签名 ────┘

  把第一段丢进 Base64 解码器 → {"alg":"HS256","typ":"JWT"}
  把第二段丢进去 → {"name":"Tom","iat":1516239022}
  第三段解不出来（它不是 Base64 编码的 JSON，是哈希值）

## 四、底部橙色条：Base64 是什么

    Base64：是一种基于 64 个可打印字符（A-Z a-z 0-9 + /）
            来表示二进制数据的编码方式。

  · 一句话：**Base64 是编码，不是加密**，可逆、无需密钥、编码后体积变大约 4/3
  · 为什么用它：JWT 要在 URL / HTTP 头里传，必须全是可打印字符，且不能有回车换行
  · JWT 实际用的是 **Base64URL** 变体：把 `+` 换成 `-`、`/` 换成 `_`、去掉末尾 `=` 填充
  · 因为它可逆，所以「JWT 里存的东西是能被人看到的」这条结论要记死

## 五、易错点

| 坑 | 说明 |
| --- | --- |
| 以为 JWT 是加密 | 前三段只有第三段算不出来，前两段随便解 |
| 把 password 放 claims | 前端随手一解就泄露，属于安全事故 |
| Header 写 "type" | 课件笔误，标准是 "typ"；手写 token 时会被验签失败 |
| iat 用毫秒 | 时间戳会变成几万年后的未来时间，exp 判断逻辑全乱 |
| 以为改了 Payload 也没事 | 服务端重算签名 ≠ 令牌里的签名 → 抛 SignatureException |

## 六、口诀

    Header 记算法，Payload 装数据，Signature 防篡改。
    三段点连接，前两段可解，最后一段算出来。
    Base64 只编码不加密，密码别往里面塞。

# ══════ JWT 令牌 —— 生成 / 解析 ══════

## 一、图上给的两个动作（就两句话）

    ① 引入 jjwt 的依赖
    ② 调用官方提供的工具类 Jwts 来生成或解析 jwt 令牌

  · 生成 = `Jwts.builder()...compact()`
  · 解析 = `Jwts.parser()...getBody()`
  · 记住：**这是一个"制造"和"验证"的对称过程，算法和密钥必须完全一致**

## 二、第 ① 步：pom.xml 引入依赖

    <dependency>
        <groupId>io.jsonwebtoken</groupId>
        <artifactId>jjwt</artifactId>
        <version>0.9.1</version>
    </dependency>

  · 0.9.1 是**一个 jar 全包**（黑马课件用的就是这版，API 最简）
  · 0.11.x / 0.12.x 拆成三件套：jjwt-api + jjwt-impl + jjwt-jackson，且 API 大改：
      signWith(Key) 传 SecretKey 对象、Jwts.parserBuilder() 替代 Jwts.parser()
  · 照 0.9.1 教程抄却引了高版本 → 编译不过，这是新手最常踩的版本坑

## 三、第 ② 步上：生成令牌（图上被遮挡部分已补全）

    @Test
    public void testGenJwt() {
        Map<String, Object> claims = new HashMap<>();
        claims.put("id", 1);
        claims.put("username", "Tom");

        String jwt = Jwts.builder()
                .setClaims(claims)                                        // 自定义载荷
                .signWith(SignatureAlgorithm.HS256, "SVRIRUlNQQ==")       // 算法 + 密钥
                .setExpiration(new Date(System.currentTimeMillis() + 3600 * 1000))  // 1 小时后过期
                .compact();                                               // 生成字符串

        System.out.println(jwt);
    }

  方法链对比：

| 方法 | 作用 | 备注 |
| --- | --- | --- |
| setClaims(map) | 覆盖式设置载荷 | 多次调用会**整体替换**，不是追加 |
| addClaims(map) | 追加式设置载荷 | tlias 里用 addClaims |
| signWith(alg, key) | 指定算法 + 密钥 | 0.9.1 传 String |
| setExpiration(Date) | 设置过期时间 | 不设 = 永不过期，很危险 |
| compact() | 生成最终 token 字符串 | 必须最后调用 |

## 四、第 ② 步下：解析令牌（图上可见的原样）

    @Test
    public void testParseJwt() throws Exception {
        String jwtToken = "eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...";   // 上一步打印出来的令牌

        Claims claims = Jwts.parser()
                .setSigningKey("SVRIRUlNQQ==")      // 与生成时的密钥一致
                .parseClaimsJws(jwtToken)           // 解析 + 验签 + 验过期
                .getBody();                         // 取出载荷

        System.out.println(claims);
    }

  打印结果形如：{id=1, username=Tom, exp=1516242622}

  取值方式：
    Integer id = (Integer) claims.get("id");       // Object 要强转
    String username = claims.get("username", String.class);   // 0.11+ 支持带类型

## 五、那个奇怪的密钥 "SVRIRUlNQQ==" 是什么

  · 0.9.1 里 `signWith(alg, String)` 和 `setSigningKey(String)` 这两个 String 重载，
    **会把字符串当成 Base64 编码去解码**，得到真正的字节密钥
  · "SVRIRUlNQQ==" 解码 → 字节 `ITHEIMA`（也就是 itheima 的大写）
  · 所以只要生成端和解析端**都写这同一个字符串**，就能对上
  · 非要避免误解，可以改成传 byte[]：`signWith(HS256, "itheima".getBytes())` + `setSigningKey("itheima".getBytes())`
    → 两端要么都传 String、要么都传 byte[]，**混用必报签名不一致**（理论层面最容易踩）

## 六、易错点（按踩坑概率排序）

| 坑 | 现象 |
| --- | --- |
| 解析端密钥和生成端不一致 | SignatureException：JWT signature does not match |
| 令牌过期后再解析 | ExpiredJwtException，异常信息里还带过期时间 |
| 令牌少一段 / 手动截断 | MalformedJwtException |
| 生成用了 byte[]，解析用 String | 签名对不上，且很难看出原因 |
| 密钥太短（0.11+） | WeakKeyException：HS256 要求密钥 ≥ 32 字节（256 bit）；0.9.1 不校验，所以低版本能跑、升级后炸 |
| 忘记 setExpiration | 令牌永久有效，泄露即永久失守 |
| 只 `setClaims` 却想追加 | 后一次调用把前面装的全覆盖掉 |
| claims 里放密码 | 任何人 Base64 解码即可读到 |

## 七、口诀

    builder 造令牌，parser 验身份；
    算法密钥两头同，多一位对上才认；
    compact 出成品，getBody 拿载荷；
    signature 对不住，一切免谈。

---

  · 一句话串起两页：**第一页讲"为什么长这样"（三段 + Base64 + 签名），第二页讲"怎么造出来/怎么验"（jjwt 的 builder 与 parser 对称使用）**&#8203;

# tlias 实战 · 案例：登录成功后生成令牌

## 一、先看懂这张图在说什么

    浏览器 ──请求──▶ 统一拦截 ──▶ Login(生成) / Emp / Dept / Report
           ◀─响应──┘

  · 红框圈住的是「统一拦截」里的小人图标 → 所有请求都得先过这道门
  · 红字「生成」只贴在 Login 上 → **只有登录这一个人接口负责"发"令牌**
  · Emp / Dept / Report 三块没有红字 → 它们只负责"验"令牌
  · 一句话：**登录 = 签发，其他接口 = 校验**

  图下两点要求（原文）：
    1. 定义 JWT 令牌操作工具类。（基于 AI）
    2. 登录完成后，调用工具类生成 JWT 令牌，并返回。

## 二、为什么必须抽工具类（而不是把 Jwts 代码塞进 Controller）

| 不抽工具类 | 抽成 JwtUtils |
| --- | --- |
| 生成 1 处 + 解析 N 处的代码散在 Controller | 全部收敛到一处 |
| 密钥写两遍，改一处漏一处 → 验签必挂 | signKey 只有一份，天然一致 |
| 想换算法/加逻辑要翻遍项目 | 只改工具类一个方法 |
| 工具类通常是 static 方法，不需要注入 | 无 Bean 依赖，随手可用 |

  「基于 AI」的意思：这类样板代码**不用手敲**，直接让 AI 生成，但你必须能看懂三件事——
    ① 密钥（signKey）写的是什么、必须全局唯一且固定
    ② 过期时间（expire）单位是毫秒
    ③ 两个方法名（generateJwt / parseJWT）后面要到处调用

## 三、第 ① 步：JwtUtils 工具类完整代码

    public class JwtUtils {
        // 签名密钥：生成和解析必须用同一个
        private static final String signKey = "itheima";
        // 过期时间：12 小时（单位毫秒）
        private static final Long expire = 43200000L;

        // 生成 JWT 令牌
        public static String generateJwt(Map<String, Object> claims) {
            String jwt = Jwts.builder()
                    .addClaims(claims)                                          // 载荷：id/username/name
                    .signWith(SignatureAlgorithm.HS256, signKey)                // 算法 + 密钥
                    .setExpiration(new Date(System.currentTimeMillis() + expire)) // 签发时刻 + 12h
                    .compact();                                                 // 串成完整 token
            return jwt;
        }

        // 解析 JWT 令牌（验签 + 验过期，失败抛异常）
        public static Claims parseJWT(String jwt) {
            Claims claims = Jwts.parser()
                    .setSigningKey(signKey)
                    .parseClaimsJws(jwt)
                    .getBody();
            return claims;
        }
    }

  逐行解释：

| 代码 | 含义 | 说明 |
| --- | --- | --- |
| signKey | 签名密钥 | 上一页测试类的 `"SVRIRUlNQQ=="` 解码就是它的大写形式，本质是同一个密钥；只要两端字符串一致即可 |
| expire = 43200000L | 12 小时 | 算式：12 × 60 × 60 × 1000；单位搞错 → 令牌 12 毫秒就过期 |
| addClaims(claims) | 追加载荷 | 与 setClaims 区别：set 是覆盖 |
| signWith(HS256, signKey) | HS256 + 密钥 | 对称算法，签发/校验同一把钥匙 |
| setExpiration(new Date(...)) | 过期时间点 | 生成的是绝对时间 = 当前时间 + 12h |
| compact() | 出成品 | 返回 `xxx.yyy.zzz` 三段式字符串 |
| parser()...getBody() | 解析 | 内部自动做验签和过期校验，不合格就抛异常 |

## 四、第 ② 步：登录接口改造（Controller）

    @PostMapping("/login")
    public Result login(@RequestBody Emp emp) {
        log.info("登录：{}", emp.getUsername());

        Emp e = empService.login(emp);                 // 1. 查用户名 + 密码
        if (e != null) {                               // 2. 查到 = 登录成功
            Map<String, Object> claims = new HashMap<>();
            claims.put("id", e.getId());               // 3. 往载荷里塞身份信息
            claims.put("username", e.getUsername());
            claims.put("name", e.getName());

            String jwt = JwtUtils.generateJwt(claims); // 4. 签发令牌

            return Result.success(
                    new LoginInfo(e.getId(), e.getUsername(), e.getName(), jwt));
        }
        return Result.error("用户名或密码错误");          // 5. 查不到 = 失败
    }

  配套两个小东西：

    // LoginInfo：只装身份 + 令牌，绝不能直接返回 Emp
    @Data
    @NoArgsConstructor
    @AllArgsConstructor
    public class LoginInfo {
        private Integer id;
        private String username;
        private String name;
        private String token;        // 前端要存起来的那个字符串
    }

    // EmpMapper：查用户
    @Select("select * from emp where username = #{username} and password = #{password}")
    Emp getByUsernameAndPassword(String username, String password);

  ⚠️ **为什么不能 `return Result.success(e)`**
     Emp 里有 password 字段 → 序列化成 JSON 就明文回到了浏览器
     流程图上"调用工具类生成令牌，并返回"里的返回值，指的就是 LoginInfo

## 五、数据流全景（记住这条链）

    前端提交 {username, password}
        ↓
    EmpService.login → EmpMapper 查库
        ↓ 查到
    claims{id, username, name} → JwtUtils.generateJwt → token
        ↓
    LoginInfo{id, username, name, token} 返回前端
        ↓
    前端存 token（localStorage），之后每个请求头带上
        ↓
    统一拦截器用 JwtUtils.parseJWT(token) 验 → 通过才放行

## 六、易错点

| 坑 | 后果 |
| --- | --- |
| signKey 改了 / 换环境不一致 | 用户全部掉线，旧令牌验签失败 |
| expire 写成 43200000（无 L） | 编译报类型错；写成 43200 就是 43 秒过期 |
| 返回 Emp 对象 | password 泄露到前端，安全事故 |
| LoginInfo 字段叫 `jwt` 而前端取 `token` | 登录成功但前端存不到值，后续全 401 |
| 忘了 put("id") | 后续想拿当前登录人 id 只能再查库 |
| 把工具类加 @Component 再 new | 静态方法直接 `JwtUtils.xxx()` 调用即可，别搞混 |
| 密钥写死在代码里还提交到 Git | 真实项目放 yml/环境变量（后面会讲配置化） |

## 七、口诀

    登录成功才发牌，发牌只有 Login 一个口。
    工具类里三件套：密钥、过期、两个方法。
    claims 装 id/username/name，LoginInfo 接住 token。
    返回 Emp 是事故，password 会裸奔。
