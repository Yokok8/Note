# 删除部门 · 思路分析

## 一、三层架构职责（照图梳理）
| 层 | 职责 | 具体做什么 |
|---|---|---|
| **Controller** | ① 接收请求参数 ② 调用 Service 层 ③ 响应结果 | 从 `/depts?id=1` 里拿到 id |
| **Service** | 调用 Mapper 接口方法 | 转发，把 id 往下传 |
| **Mapper** | 执行 SQL | `delete from dept where id = ?` |

请求链路：浏览器 → Controller → Service → Mapper → 数据库 → 逐层返回
和查询部门的套路**完全一样**，只多了"接参数"这一步。

## 二、接口文档信息（关键三要素）
| 项 | 值 |
|---|---|
| 请求路径 | /depts |
| 请求方式 | **DELETE** |
| 请求参数 | id（number） |
| 请求样例 | /depts?id=1　/depts?id=2 |
| 响应结果 | {"code":1, "msg":"success", "data":null} |

注意 `data` 是 **null** —— 删除不需要返回数据，但**结构还是统一的 Result**。

## 三、Mapper 的 SQL
    delete from dept where id = ?

- `?` 是占位符，对应注解写法里的 `#{id}`
- **where 条件是重点**：漏了就是清空整张 dept 表

## 四、传参方式（本项目两种都可能见到）
| 方式 | URL 长什么样 | 注解 | 特点 |
|---|---|---|---|
| 查询参数 | /depts?id=1 | @RequestParam Integer id | ? 后面带参数 |
| 路径参数 | /depts/1 | @PathVariable Integer id | **更 RESTful**，后端用 @DeleteMapping("/{id}") |

判定技巧：**看 URL 里参数在 `?` 后还是拼在路径里**——在 `?` 后用 RequestParam，在路径里就用 PathVariable。

## 五、易错点
| 易错 | 说明 |
|---|---|
| delete 漏 where | **清空整张表**，和 update 忘 where 是同级事故 |
| 返回类型写 void | 最好也返回 Result，前端统一处理 |
| 参数名对不上 | URL 里叫 id，方法形参也叫 id 才不用额外指定 |
| 以为删除要返回数据 | data 为 null 是正常的 |
| 拼 SQL 用 ${} | 必须用 #{}，否则有 SQL 注入风险 |

## 六、口诀
- **接参 → 转发 → 删数据，三层套路不变**
- **DELETE 请求删数据，URL 带 id 定位**
- **删改务必带 where，漏了全表遭殃**

# Controller 接收参数 · 简单参数

场景：`DELETE /depts?id=8` —— 要把 URL 里 `id=8` 这个值取到方法里用。

## 方式一：HttpServletRequest（原始方式，不推荐）
    @DeleteMapping("/depts")
    public Result delete(HttpServletRequest request){
        String idStr = request.getParameter("id");  // 拿到的是字符串
        int id = Integer.parseInt(idStr);           // 还要手动转类型
        System.out.println("根据ID删除部门： " + id);
        return Result.success();
    }
**缺点（课件红字）**&#8203;：繁琐、手动类型转换。取什么都是 String，转 int、转日期全靠自己。

## 方式二：@RequestParam（推荐）
    @DeleteMapping("/depts")
    public Result delete(@RequestParam("id") Integer deptId){
        System.out.println("根据ID删除部门： " + deptId);
        return Result.success();
    }
- `@RequestParam("id")` 里的 id = **请求参数名**
- `Integer deptId` = 形参名，**可以不同**，靠注解绑定
- **类型转换 Spring 自动完成**，不用再 parseInt

### ⚠️ 注意点（课件红字）
`@RequestParam` 的 **required 属性默认为 true**，代表该参数**必须传递**，不传递将报错。
如果参数可选，把属性设置为 false：
    public Result delete(@RequestParam(value = "id", required = false) Integer deptId)

> 顺带记一个常用属性：`defaultValue = "1"`，不传时给默认值（和 required 搭配用）。

## 方式三：省略 @RequestParam
    @DeleteMapping("/depts")
    public Result delete(Integer id){
        System.out.println("根据ID删除部门： " + id);
        return Result.success();
    }
**前提**：请求参数名与形参变量名**相同**，才能自动接收（这里都叫 id，所以能省）。
名字不一样就必须写注解，否则接不到值（拿到 null）。

## 三种方式对比
| 方式 | 写法 | 类型转换 | 推荐度 |
|---|---|---|---|
| HttpServletRequest | request.getParameter("id") | 手动 parseInt | ★ |
| @RequestParam | @RequestParam("id") Integer deptId | 自动 | ★★★★★ |
| 省略注解 | Integer id | 自动 | ★★★★（名字必须一致） |

## 易错点
| 易错 | 说明 |
|---|---|
| 忘了传参数 | required 默认 true → 直接 400 报错 |
| 用基本类型 int 接 | 不传参数时接不了 null，用包装类 Integer 更安全 |
| 形参名和参数名不一致又没写注解 | 拿到 null，不报错，**最坑** |
| 以为 Spring 会自动转型所有类型 | 基本类型和常见类型行，特殊格式（日期）要额外处理 |

## 口诀
- **原始方式 getParameter 还带 parseInt，又长又麻烦**
- **一个 @RequestParam 搞定绑定 + 转型**
- **名字相同可省注解，required 默认必传**

# 删除部门 · 功能实现（三层完整代码）

## 一、DeptController
    @DeleteMapping("/depts")
    public Result delete(Integer id){
        System.out.println("根据ID删除部门数据： " + id);
        deptService.delete(id);
        return Result.success();
    }
- `@DeleteMapping("/depts")`：映射 **DELETE** 方式的 /depts 请求
- `Integer id`：这里是**方式三**（省略 @RequestParam）—— 请求参数名 id 和形参名 id 相同，自动接收
- 调完 Service 直接 `return Result.success()`，因为删除没有数据要返回

## 二、DeptServiceImpl
    @Override
    public void delete(Integer id) {
        deptMapper.delete(id);
    }
- 返回类型是 **void** —— 不需要把结果往上传
- @Override 表示重写接口方法

## 三、DeptMapper
    @Delete("delete from dept where id = #{id}")
    void delete(Integer id);
- `@Delete`：MyBatis 提供的注解，专门放删除 SQL
- `#{id}`：**占位符**，对应方法形参 id（预编译，防 SQL 注入）
- 返回类型也是 **void**

## 四、⭐ 最容易看错的一点：返回值不一样
| 层 | 查询 findAll | 删除 delete |
|---|---|---|
| Controller | Result | **Result** |
| Service | List\<Dept\> | **void** |
| Mapper | List\<Dept\> | **void** |

规律：
- **只有 Controller 返回 Result**（要给前端统一格式）
- Service / Mapper 的删除方法**不用返回任何东西**，因为删完就完事了
- 查询必须层层往上带数据，删除不需要，所以是 void

## 五、和上一页的呼应
上一页讲了接参的三种方式，这份代码用的是**方式三**（省略 @RequestParam）。
为什么能省：**形参名 `id` 和请求参数名 `id` 一模一样**。要是形参写成 `deptId`，就必须写 `@RequestParam("id")`。

## 六、易错点
| 易错 | 说明 |
|---|---|
| Service/Mapper 写成返回 Result | 不符合分层，Mapper 只认数据不认 Result |
| SQL 漏 where | **清空整张表** |
| `#{id}` 写成 `${id}` | 变成字符串拼接，有注入风险 |
| 忘写 @Delete，只写 @Select | 语法错误/执行出错 |
| void 方法里 return 值 | 编译不过 |
| 形参改名字后忘写注解 | 接不到值，变成 null 删除条件失效 |

## 七、口诀
- **Controller 收参、传 id、回 Result；Service/Mapper 只管删，返回 void**
- **@Delete 贴方法，SQL 用 #{} 占位**
- **删改必带 where，一个都不能少**
