# 部门查询 · 思路分析

## 一、需求（先明确再动手）
- 1.1 部门数据量较少 → **不考虑分页展示**
- 1.2 查询结果 → **按最后修改时间倒序排序**

这两条直接决定了 SQL 的写法（不用 limit、要 order by update_time desc），也决定了 Controller 返回的是**全部数据的 List**。

## 二、三层架构各自的职责（查询功能）
| 层 | 职责 | 本项目里具体做什么 |
|---|---|---|
| **Controller** | ① 接收请求 ② 调用 Service 层 ③ 响应结果 | 定义 `@GetMapping("/depts")`，拿到 List 后封装成 Result 返回 |
| **Service** | 调用 Mapper 接口方法 | 转发调用，把结果往上抛 |
| **Mapper** | 执行 SQL，操作数据库 | 查 dept 表 |

调用链：
浏览器请求 → Controller → Service → Mapper → 数据库
浏览器响应 ← Controller ← Service ← Mapper ← 数据库

**一句话记法**：Controller 只负责**接和回**，Service 负责**算**，Mapper 负责**存取**。

## 三、Mapper 层的 SQL
    select * from dept order by update_time desc

拆开看：
- `select *` —— 查全部列
- `from dept` —— 部门表
- `order by update_time desc` —— 按**最后修改时间**倒序（对应需求 1.2）
- 没有 limit —— 因为不分页（对应需求 1.1）

## 四、易错点
| 易错 | 说明 |
|---|---|
| 需求没看清就写 SQL | 需求 1.2 明确要按 update_time 倒序，漏了 order by 功能就错了 |
| 排序字段写成 create_time | 是**最后修改时间** update_time，不是创建时间 |
| 概念上越层 | Controller 里直接调 Mapper 也能跑，但破坏了分层 → Service 必须存在 |
| select * 上生产 | 课件为了简洁用了 *，规范写法是写出全部字段名（性能 + 语义清晰） |

## 五、口诀
- **数据少不分页，按修改时间倒序**
- **Controller 接和回、Service 算、Mapper 存取**
- **SQL 就是个 select * from dept order by update_time desc**

# 部门查询 · 功能实现（三层完整代码）

## 一、Controller：接收请求，处理响应
    @RestController
    public class DeptController {
        @Autowired
        private DeptService deptService;

        @GetMapping("/depts")
        public Result findAll(){
            List<Dept> deptList = deptService.findAll();
            return Result.success(deptList);
        }
    }
- @RestController：既能被扫描成 Bean，又能把返回值转成 JSON
- @Autowired：把 DeptService 对象注入进来用
- @GetMapping("/depts")：浏览器请求 /depts 时交给这个方法
- 返回类型是 **Result**（统一响应结果），不是 List

## 二、Service：业务处理
    @Service
    public class DeptServiceImpl implements DeptService {
        @Autowired
        private DeptMapper deptMapper;

        @Override
        public List<Dept> findAll() {
            return deptMapper.findAll();
        }
    }
- 接口 DeptService 定规范，实现类 DeptServiceImpl 干活
- 本功能没复杂业务逻辑，所以就是**转手调用** Mapper
- @Service 写在**实现类**上，写接口上无效

## 三、Dao/Mapper：数据访问操作（增删改查）
    @Mapper
    public interface DeptMapper {
        /**
         * 查询全部部门
         */
        @Select("select * from dept order by update_time desc")
        public List<Dept> findAll();
    }
- 只有接口没有实现类，MyBatis 用**动态代理**生成实现
- @Select 里直接写 SQL，返回值自动封装成 List\<Dept\>
- order by update_time desc 对应需求"按最后修改时间倒序"

## 四、三层对照速查
| 层 | 类 | 注解 | 干的事 |
|---|---|---|---|
| Controller 接收请求、处理响应 | DeptController | @RestController | 接请求 → 调 Service → 包 Result 返回 |
| Service 业务处理 | DeptServiceImpl | @Service | 调 Mapper，返回数据 |
| Dao/Mapper 数据访问 | DeptMapper | @Mapper | 执行 SQL，查 dept 表 |

## 五、必须注意
| 注意点 | 说明 |
|---|---|
| 方法名大小写 | 图上是 findALL()，**是课件笔误**，正确写 findAll() |
| Result.success() | Result 类里必须有这个静态方法，否则编译不过 |
| 返回类型 | Controller 返回 Result，Service/Mapper 返回 List\<Dept\> |
| @Mapper 别丢 | 少了它启动报找不到 Bean |
| SQL 字段 | 图上用 select *，规范写法是写出全部字段名 |

## 六、口诀
- **Controller 接请求、Service 办业务、Mapper 存取数据**
- **注解贴对位置：RestController 在 Controller、Service 在实现类、Mapper 在接口**
- **一层调一层，最后包 Result**

# 数据封装（实体类属性名 vs 数据库字段名）

## 一、问题现象
查询能查到数据，但 `createTime`、`updateTime` 两个字段**全是 null**。
原因：**实体类属性名和数据库表查询返回的字段名不一致时，MyBatis 不能自动封装。**&#8203;

| | Java 实体类 Dept | dept 表字段 | 能否自动封装 |
|---|---|---|---|
| 1 | id | id | ✔ 一致 |
| 2 | name | name | ✔ 一致 |
| 3 | createTime | create_time | ✘ 不一致 → **null** |
| 4 | updateTime | update_time | ✘ 不一致 → **null** |

记忆点：**Java 用驼峰 createTime，数据库用下划线 create_time**，所以老是对不上。

## 二、三种解决方案

### 方案 ① 手动结果映射：@Results + @Result
    @Results({
        @Result(column = "create_time", property = "createTime"),
        @Result(column = "update_time", property = "updateTime")
    })
    @Select("select id, name, create_time, update_time from dept order by update_time desc")
    public List<Dept> findAll();

- `column` 写**数据库字段名**，`property` 写**实体类属性名**
- 缺点：每个方法都要写一遍，字段多了很啰嗦

### 方案 ② SQL 里起别名
    @Select("select id, name, create_time createTime, update_time updateTime from dept order by update_time desc")
    public List<Dept> findAll();

- 给列起**和属性名一样**的别名（`create_time createTime`，中间空格即可）
- 缺点：改字段名要挨个方法改

### 方案 ③ 开启驼峰命名（课件标"推荐"）
在 application.yml 中：
    mybatis:
      configuration:
        map-underscore-to-camel-case: true

- 原理：字段名与属性名符合**驼峰规则**时，MyBatis 自动把下划线转驼峰映射
- 前提：`create_time` → `createTime` 这种**下划线转驼峰**的对应关系才行；`dept_name` → `dname` 这种它就管不了
- 优点：**配一次，全局生效**，所有 Mapper 都受益

## 三、三方案对比
| 方案 | 改哪里 | 生效范围 | 推荐度 |
|---|---|---|---|
| @Results 手动映射 | Java 注解 | 只对该方法 | 字段少、个别不一致时用 |
| SQL 起别名 | SQL 语句 | 只对该语句 | 临时救急 |
| 开启驼峰命名 | yml 配置 | **全局所有查询** | ★★★★★ |

## 四、易错点
| 易错 | 说明 |
|---|---|
| 属性名对不上不报错，只是 null | 不抛异常，**最坑**——一定要检查返回数据 |
| yml 里 configuration 缩进写错 | mybatis → configuration → map-underscore-to-camel-case 逐级缩进 |
| 开了驼峰还写 @Results | 不冲突，但没必要，重复 |
| 指望驼峰映射万能 | 只解决"下划线 ↔ 驼峰"，其他不一致还得用别名或 @Results |

## 五、口诀
- **名字一致自动封装，名字不一致就是 null**
- **三种解法：@Results 映射、SQL 起别名、开驼峰命名**
- **生产就开驼峰：map-underscore-to-camel-case = true**
