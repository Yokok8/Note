# 员工登录 · 思路

## 一、需求

登录页只有两个输入框加一个「登录」按钮：

| 元素 | 说明 |
|---|---|
| 账号输入框 | 对应 `emp.username` |
| 密码输入框 | 对应 `emp.password` |
| 登录按钮 | 提交到后端校验 |
| 重置按钮 | 清空输入框（纯前端行为） |
 
只要账号密码和数据库里的一条 `emp` 记录**同时匹配**，就算登录成功，可以进入系统主页面。

## 二、三层职责（图上的原文，完整重述）

    Chrome 浏览器 → Controller → Service → Mapper → MySQL

| 层 | 职责（课件原文） |
|---|---|
| **Controller** | ① 接收请求参数（**用户名、密码**）② 调用 Service 方法 ③ 响应结果 |
| **Service** | ① **根据用户名和密码查询员工信息** ② **判定，组装数据并返回** |
| **Mapper** | 执行 SQL：`select * from emp where username = ? and password = ?` |

图底部那行「**三层架构每一层的制作**」是在提醒：这一节的重点不是某个技术点，而是**按三层分工把一个登录功能做出来**。

## 三、SQL 是关键（也是最容易出问题的地方）

    select * from emp where username = ? and password = ?

### 逐段解读

| 片段                   | 说明                       |
| -------------------- | ------------------------ |
| `select *`           | 查出该行所有字段（后面会说这个 `*` 有隐患） |
| `where username = ?` | 用户名精确匹配                  |
| `and password = ?`   | 密码精确匹配                   |
| `and`                | **两个条件必须同时成立**，缺一不可      |

- 用 `and` 而不是 `or`：`or` 会导致"用户名对但密码错"也能查出来，等于谁都能登录
- 参数用 `?` 占位符（`#{}`），**绝不能用 `${}` 拼接**，否则就是教科书级的 SQL 注入

### 这条 SQL 的天然特点：查不到就是 null

| 情况 | 查询结果 |
|---|---|
| 用户名对、密码对 | 返回 1 条 Emp 记录 |
| 用户名对、密码错 | **null** |
| 用户名不存在 | **null** |

**这两种失败情况返回的都是 null，后端无法区分"用户不存在"和"密码错误"。**&#8203; 这不是缺陷，反而是安全实践——统一提示"用户名或密码错误"，避免攻击者用提示语探测哪些账号存在。

## 四、Service 的"判定"在做什么

图里 Service 第 ② 步只写了"判定，组装数据并返回"六个字，展开就是：

| 判定结果 | 后端动作 |
|---|---|
| `emp == null`（没查到） | 登录失败 → 返回错误提示 |
| `emp != null`（查到了） | 登录成功 → **签发 token**，和员工信息一起返回 |

### 图上右上角那句备注的含义

图右上角写着「**我签发的是 token**」，这是老师给的关键提示：

- 登录成功后**不能只返回"成功"两个字**，要返回一个**凭证**，让前端后续请求带着它证明"我已经登录过了"
- 这个凭证就是 **JWT token**（一串加密字符串）
- 前端把它存到 localStorage，之后每次请求放在请求头里；后端用拦截器校验

所以登录接口的返回结构大概是这样：

    {
      "code": 1,
      "msg": "success",
      "data": {
        "id": 1,
        "username": "songjiang",
        "name": "宋江",
        "token": "eyJhbGciOiJIUzI1NiJ9.eyJpZCI6MS..."
      }
    }

- `data` 里既有员工基本信息（前端用来显示"欢迎，宋江"），又有 `token`
- token 的生成和校验是**后续章节**的内容，这一节先把"查到人 → 要发 token"这个位置留出来

## 五、接口设计

| 项 | 内容 |
|---|---|
| 请求方式 | **POST**（登录涉及密码，不能放 URL 上） |
| 请求路径 | `/login` |
| 参数格式 | **JSON 请求体**（不是查询参数） |
| 返回 | `Result`，`data` 里装 id + username + name + **token** |

请求体：

    {
      "username": "songjiang",
      "password": "123456"
    }

- 因为参数在请求体里，Controller 必须用 **`@RequestBody`**
- 用查询参数（`?username=xx&password=xx`）会把密码暴露在 URL 和服务器访问日志里，绝对不行

## 六、三层代码骨架（先有框架感，具体实现下一节）

### Controller

    @PostMapping("/login")
    public Result login(@RequestBody Emp emp) {
        log.info("员工登录：{}", emp.getUsername());
        LoginInfo loginInfo = empService.login(emp);
        return Result.success(loginInfo);
    }

- 用 `Emp` 接收请求体就行，因为 JSON 的 `username`、`password` 正好是 Emp 的属性
- ⚠️ 日志里**只打用户名，不打密码**，否则密码明文进日志文件

### Service

    public LoginInfo login(Emp emp);

    @Override
    public LoginInfo login(Emp emp) {
        // 1. 根据用户名和密码查询员工
        Emp e = empMapper.getByUsernameAndPassword(emp);

        // 2. 判定
        if (e == null) {
            return null;      // 或抛自定义异常，交给全局异常处理器
        }

        // 3. 组装数据（含 token）
        LoginInfo info = new LoginInfo();
        info.setId(e.getId());
        info.setUsername(e.getUsername());
        info.setName(e.getName());
        info.setToken(JwtUtils.generate(e));    // 签发 token（后续章节）
        return info;
    }

### Mapper

    @Select("select * from emp where username = #{username} and password = #{password}")
    Emp getByUsernameAndPassword(Emp emp);

- 返回 **单个 `Emp`**，不是 `List<Emp>`（`username` 应当唯一，最多一条）
- `#{username}` 取的是**参数对象的属性**（对象传参时 `#{}` 里写属性名）

## 七、这条 SQL 留下的三个隐患（后面章节会处理）

| 隐患 | 后果 | 改进方向 |
|---|---|---|
| **密码明文存库** | 数据库被拖走就等于所有账号泄露 | 存 **MD5 / BCrypt** 加密后的值，登录时把输入密码加密后比对 |
| **`select *` 查出全部字段** | 把 password 也查出来带到了内存（还容易误返给前端） | 只查需要的列：`select id, username, name ...` |
| **token 还没做** | 前端登录后无法证明身份，接口全裸奔 | JWT 生成 + 拦截器校验（后续章节） |

另外还有一个设计层面的问题：**Controller 直接把 `Emp` 当接收参数**，登录成功后如果返回 Emp 对象，`password` 字段也会被序列化进 JSON 返回给前端。所以实际实现要**新建一个 `LoginInfo` / `LoginVO` 只装需要返回的字段**，这也是图上 Service 那句「组装数据」的真正含义。

## 八、易错点

| 问题 | 后果 |
|---|---|
| SQL 用 `or` 连接 | 用户名对或密码对就能登录，等于**没有校验** |
| SQL 用 `${}` 拼参数 | SQL 注入，输入 `' or '1'='1` 直接绕过登录 |
| 用 GET 传密码 | 密码出现在 URL、浏览器历史、服务器日志里 |
| Controller 漏 `@RequestBody` | 参数全为 null，永远登录失败 |
| Mapper 返回 `List<Emp>` 却在 Service 里判 `!= null` | 空列表也不是 null，**永远判定成功** |
| 判定条件写成 `emp.getId() == null` | id 为 null 就 NPE，应先判对象本身 |
| 返回 Emp 对象给前端 | password 被序列化出去，**泄漏密码** |
| 日志打印整个 Emp | 密码明文进日志文件 |
| 失败时返回不同的提示语 | "用户不存在" / "密码错误" 两种提示会帮攻击者枚举账号 |
| 只返回"登录成功"不发 token | 前端无法维持登录状态，每个接口都得重新传账号密码 |

## 九、口诀

> **登录 = 按用户名和密码查一条记录，查到就成功、查不到就失败**
> **SQL 用 and 连接、`#{}` 传参，两种失败都返回 null，统一提示"用户名或密码错误"**&#8203;
> **Service 两步：查（Mapper）+ 判定组装（签发 token）**&#8203;
> **Controller 用 POST + `@RequestBody`，返回 LoginInfo 而不是 Emp**
> **不要明文存密码，不要 `select *`，日志别打密码**

# 登录校验思路 + 会话技术

## 一、问题从哪来

HTTP 是**无状态**协议：每个请求都是独立的，服务器处理完一个请求就忘了是谁发的。

所以登录之后，下一次请求查员工列表时，服务器根本不知道"你是谁"。

**登录校验要解决的就是这件事：让后续每次请求都能带上"我已登录"的证明。**&#8203;

## 二、登录校验的架构（图 1）

### 图上的四个部分

| 部分               | 作用                                   |
| ---------------- | ------------------------------------ |
| **浏览器**          | 发起请求、接收响应                            |
| **统一拦截**         | 挡在所有 Controller 前面，**统一做校验**，校验通过才放行 |
| **Controller 层** | Login、Emp、Dept、Report 四组接口           |
| **登录标记**         | 存"谁登录过"这个信息的地方                       |

### 请求怎么走（五步）

| 步骤 | 发生什么 |
|---|---|
| 1 | 浏览器发请求 |
| 2 | 请求**不直接进 Controller**，先到「统一拦截」 |
| 3 | 拦截器从「登录标记」里**取**凭证，校验该请求是否已登录 |
| 4 | 校验通过 → **放行**到对应的 Controller（Emp / Dept / Report） |
| 5 | Controller 处理完 → 响应再经拦截器**返回**浏览器 |

### 两条特别路径

| 路径 | 谁 → 谁 | 说明 |
|---|---|---|
| **存**（实线） | Login → 登录标记 | 登录成功后，把凭证写入标记 |
| **取**（虚线） | 登录标记 → 统一拦截 | 之后每次请求，拦截器从标记里读出来校验 |

为什么不校验登录接口本身：`Login` 是**唯一不需要拦截**的接口，因为它就是用来产生凭证的，还没有凭证可校验。

### 图上的两条标注（原文）

> **登录标记：用户登录成功之后，在后续的每一次请求中，都可以获取到该标记。【会话技术】**
> **统一拦截：过滤器 Filter、拦截器 Interceptor**

这两句是本页的骨架：

- **登录标记 ≠ 一个变量**，而是要靠"会话技术"实现——数据要能**跨多次请求**存活
- **统一拦截有两种实现**：Filter（Servlet 规范，粒度粗）和 Interceptor（Spring MVC，能拿到方法信息，本课程用后者）

## 三、会话技术（图 2）

### 3.1 什么是会话（原文）

> **会话：用户打开浏览器，访问 web 服务器的资源，会话建立，直到有一方断开连接，会话结束。在一次会话中可以包含多次请求和响应。**&#8203;

拆开看：

| 关键词 | 含义 |
|---|---|
| **打开浏览器开始** | 会话的起点 |
| **包含多次请求和响应** | 一次会话 ≠ 一次请求，可能几十上百次 |
| **一方断开连接结束** | 关浏览器、超时、服务器重启都可能结束 |

### 3.2 什么是会话跟踪（原文，红线那句是重点）

> **会话跟踪：一种维护浏览器状态的方法，服务器需要识别多次请求是否来自于同一浏览器，以便在同一次会话的多次请求间共享数据。**&#8203;

三个关键点：

| 点 | 意思 |
|---|---|
| **维护浏览器状态** | 让无状态的 HTTP 看起来"记得住人" |
| **识别是否同一浏览器** | 服务器要能判断：这三个请求是同一个人发的吗 |
| **共享数据**（红线） | 这才是目的——第一次请求存进去的东西，第二次能取出来 |

**理解口诀：会话技术 = 让"无状态"的 HTTP 在多次请求之间共享数据。**&#8203;

### 3.3 三种会话跟踪方案（原文）

| 方案 | 类别 | 数据存在哪 |
|---|---|---|
| **Cookie** | 客户端会话跟踪技术 | **浏览器**（用户机器上） |
| **Session** | 服务端会话跟踪技术 | **服务器内存**（每个用户一个对象） |
| **令牌技术** | 令牌（JWT） | **客户端存 token，服务器不存** |

图下方那个"+"号是在提示：**令牌技术是后来加的方案**，也是本课程最终采用的。

## 四、两页之间的关系

    图 1「登录校验思路」  →  提出需求：需要一个能跨请求存活的"登录标记"
    图 2「会话技术」      →  回答用什么实现：Cookie / Session / 令牌

- 图 1 是**架构设计**（放在哪、怎么拦）
- 图 2 是**技术选型**（用什么存、用什么传）
- 后续章节：JWT 生成 token → 拦截器校验 token

## 五、易错点

| 问题 | 后果 |
|---|---|
| 以为登录接口也要拦截 | 登录时还没有凭证，永远进不去，**死循环** |
| 把"会话"理解成"一次请求" | 拦截器就没意义了，一次会话包含多次请求 |
| 只做了登录接口，没做统一拦截 | 登录功能等于**形同虚设**，直接调 `/emps` 就能拿数据 |
| 用 Session 却部署多台服务器 | A 台登录、B 台不认，用户莫名被踢下线 |
| Cookie 里存密码或用户信息 | 用户可直接篡改，越权风险 |
| 拦截器里校验失败不返回 | 请求卡住或抛 500，前端拿不到明确提示 |
| 把 token 放 URL 参数里传 | 会进浏览器历史和服务器日志，泄露风险 |
| 认为 JWT 能主动失效 | 做不到，需要配合黑名单或短有效期 |

## 六、口诀

> **HTTP 无状态 → 需要"登录标记"跨请求存活 → 这就是会话技术**
> **请求先过统一拦截，校验通过才放行到 Controller；登录接口本身不拦**
> **登录标记靠会话技术实现；统一拦截用 Filter 或 Interceptor**
> **Cookie 存客户端（不安全）、Session 存服务端（集群难）、JWT 两边都不存（无状态）**&#8203;
> **前后端分离 + 集群 → 选令牌**

# 会话跟踪方案（一）· Cookie

## 一、Cookie 怎么工作（图上半部分）

### 一次完整的往返

    ① 登录成功
       服务器响应头：Set-Cookie: name=value
            ↓
    ② 浏览器把这个 name=value 按"域名"存起来
            ↓
    ③ 之后每次请求，浏览器自动带上
       请求头：Cookie: name=value
            ↓
    ④ 统一拦截从请求里取出 Cookie 校验

### 两个方向的关键点

| 方向 | 头字段 | 谁写 | 时机 |
|---|---|---|---|
| **响应**（服务器 → 浏览器） | `Set-Cookie: name=value` | 服务器设置 | 登录成功后下发 |
| **请求**（浏览器 → 服务器） | `Cookie: name=value` | **浏览器自动加** | 之后每次请求 |

**重点：第 ③ 步是浏览器自动完成的，Java 代码里根本不用写。**&#8203; 这是 Cookie 最"省事"的地方，也是它被 HTTP 协议原生支持的意思。

## 二、优缺点（图上原文）

### 优点

> **优点：HTTP 协议中支持的技术**

- 意思是不用引任何依赖、不用改任何配置，**浏览器天生就支持**
- 服务端只需要 `response.addCookie(...)` 或直接写响应头
- 所有浏览器通用，没有兼容性问题

### 缺点（三条）

| 缺点                      | 原因                                                           |
| ----------------------- | ------------------------------------------------------------ |
| **移动端 APP 无法使用 Cookie** | Cookie 是**浏览器**的功能，App 没有浏览器环境。Android/iOS 原生请求不会自动维护 Cookie |
| **不安全，用户可以自己禁用 Cookie** | ① 数据**明文存在用户机器上**，改个值就能伪造身份；② 浏览器设置里可以直接关掉 Cookie，功能全废       |
| **Cookie 不能跨域**         | 同源策略限制，前端一个端口、后端另一个端口就带不过去（下面重点讲）                            |

## 三、跨域到底怎么判断（图下半部分）

### 课件原文

> **跨域区分三个维度：协议、IP/域名、端口**

**三个维度中只要有一个不同，就是跨域。**&#8203;

### 图上的场景

| 位置 | 地址 |
|---|---|
| 当前登录页面 | `http://192.168.150.200:90/login.html` |
| 前端服务器 | `192.168.150.200:90` |
| 后端服务器 | `192.168.150.100:8080` |

前端往 `http://192.168.150.100:8080/login` 发请求时，**Cookie 被标了红叉** —— 因为：

| 维度 | 页面 | 后端 | 是否相同 |
|---|---|---|---|
| 协议 | http | http | ✅ 同 |
| IP | 192.168.150.200 | 192.168.150.100 | ❌ **不同** |
| 端口 | 90 | 8080 | ❌ **不同** |

### 最容易被忽略的：端口不同也是跨域

同一个 IP、同一个协议，**只换了端口号，照样跨域**：

    http://192.168.150.200:90     ← 页面
    http://192.168.150.200:9090   ← 请求 → 跨域！

很多人以为"域名一样就不是跨域"，实际上端口变了就算。

### 一个反直觉的点

- **同源策略是浏览器加的限制**，不是服务器
- 服务器 A 用代码调服务器 B 的接口，**完全不受跨域限制**（后端之间调用没有这个概念）
- 跨域只发生在**浏览器里的 JS 发请求**这个场景

## 四、为什么 tlias 用不了 Cookie

    tlias 采用前后端分离：
        前端页面  运行在 http://localhost:90
        后端接口  运行在 http://localhost:8080

- 协议相同、IP 相同，**端口不同 → 跨域**
- Cookie 带不过去 → 后端拿不到 `name=value` → 拦截器永远判定"未登录"
- 就算费劲配 CORS、`withCredentials` 把 Cookie 硬带过去，**移动端 APP 那条缺点还是绕不过**

**结论：Cookie 这条路在前后端分离的项目里基本走不通，所以课件把它列为"方案一"就带过去了。**&#8203;

## 五、Cookie 的常用属性（课件没讲，实战要知道）

| 属性 | 作用 |
|---|---|
| `Max-Age` / `Expires` | 过期时间，不设就是"关闭浏览器即失效" |
| `Path` | 哪些路径下的请求要带上这个 Cookie |
| `Domain` | 哪个域名下有效 |
| **`HttpOnly`** | JS 读不到（`document.cookie` 取不出），**防 XSS 偷 Cookie** |
| **`Secure`** | 只在 HTTPS 下发送 |
| **`SameSite`** | 控制跨站请求是否带上（Strict / Lax / None） |

- 真要存凭证，`HttpOnly` 必开，否则一行 JS 就能把凭证读走
- 但即使全开，**Cookie 依然解决不了跨域和移动端问题**

## 六、三种方案的定位（把 Cookie 放回队列里）

| 方案 | 一句话 | 卡在哪 |
|---|---|---|
| **Cookie** | 浏览器自动存取的小文本 | 跨域、移动端、不安全 |
| **Session** | 数据在服务器，靠 Cookie 传 ID | 依然依赖 Cookie；集群不共享 |
| **JWT 令牌** | 服务器签发、客户端存、请求头带 | 本项目选它 |

**Cookie 是 Session 的"地基"**&#8203;——Session 之所以能认出你是谁，靠的就是 Cookie 里那个 `JSESSIONID`。所以 Cookie 跨域，Session 也跟着废了一半。

## 七、易错点

| 问题 | 说明 |
|---|---|
| 以为只有域名不同才算跨域 | **端口不同、协议不同都算**，三个维度任一不同即跨域 |
| 以为服务器调服务器也受跨域限制 | 不受，同源策略是**浏览器**的限制 |
| Cookie 里存用户信息或密码 | 明文存用户机器上，改了就能伪造 |
| 忘了 Cookie 有 4KB 大小限制 | 存多了会被截断 |
| 以为前端能读到所有 Cookie | 加了 `HttpOnly` 的 JS 读不到（这是保护，不是 bug） |
| 以为 APP 也能用 Cookie | 只有浏览器环境有，App 得自己实现存储 |
| 用户禁用 Cookie 就没救 | 功能直接失效，没有兜底方案 |
| 前后端分离还想用 Cookie 存登录态 | 端口不同就跨域，硬配也能通但很别扭，不如换令牌 |

## 八、口诀

> **服务器 Set-Cookie 下发，浏览器自动保存，之后每次请求自动带 Cookie**
> **优点就一条：HTTP 原生支持，不用额外技术**
> **缺点三条：APP 用不了、不安全能被禁用、不能跨域**
> **跨域看三个维度：协议、IP/域名、端口，任一不同即跨域（端口不同也算！）**&#8203;
> **前后端分离端口不一样 → Cookie 带不过去 → 换令牌**

# 会话跟踪方案（二）· Session

## 一、Session 怎么工作（图上半部分）

### 一次完整的往返

    ① 登录成功
       服务器创建 HttpSession 对象，把用户信息存进去
       session.setAttribute("loginUser", emp.getUsername());
            ↓
    ② 响应头带下去一个 ID
       Set-Cookie: JSESSIONID=1
            ↓
    ③ 浏览器之后每次请求自动带上
       Cookie: JSESSIONID=1
            ↓
    ④ 服务器按这个 ID 去内存里找到对应的 HttpSession
       取出登录标记 → 校验通过

### 和 Cookie 的关键差别

| | Cookie | Session |
|---|---|---|
| 数据存在哪 | **浏览器**（用户机器） | **服务器内存** |
| 传的是什么 | **数据本身** | **只是一个 ID**（JSESSIONID） |
| 用户能不能改 | ✅ 能改能看 | ❌ 看不到，只能看到一个 ID |

**一句话：Session 是"数据放服务器，只把钥匙（JSESSIONID）交给浏览器"。**&#8203;

### 图上的 Session 标签

四个 Controller 右侧分别挂着 `Session(1)`、`Session(2)`、`Session(1)`、`Session(1)`，意思是：

- 每个登录的用户在服务器内存里**各有一个独立的 Session 对象**
- 张三进来拿的是 `Session(1)`，李四进来拿的是 `Session(2)`
- 哪个 Controller 处理请求不重要，**关键是这个请求带的是哪个 JSESSIONID**

## 二、优缺点（图上原文）

### 优点

> **优点：存储在服务端，安全**

- 数据在服务器内存里，用户**既看不到也改不了**
- 解决了 Cookie "明文存储、可以被篡改" 的问题
- 可以存任意 Java 对象（Emp、List 都行），不像 Cookie 只能存字符串

### 缺点（两条）

| 缺点 | 具体表现 |
|---|---|
| **服务器集群环境下无法直接使用 Session** | Session 只存在创建它的那台机器的内存里，请求换了机器就找不到（下面详细讲） |
| **Cookie 的缺点** | Session 靠 JSESSIONID 传，而 JSESSIONID 本身就是 Cookie → **Cookie 跨域、移动端用不了这两条，Session 一条不落全有** |

## 三、集群环境下为什么会失效（图下半部分）

### 场景

    浏览器（JSESSIONID=1）
        ↓
    服务器（负载均衡：轮询分发）
        ↓ 分到哪台不确定
    服务器 1 / 服务器 2 / 服务器 3

### 两次请求的对比

| 请求 | 被分发到 | 结果 |
|---|---|---|
| 第 1 次（登录） | 服务器 1 | 创建了 `Session(1)`，存在这台的内存里 |
| 第 2 次（查员工） | **服务器 2** | 服务器 2 的内存里**没有 `Session(1)`** → 认不出用户 |

- 浏览器带的 `JSESSIONID=1` 是对的，**但这个 ID 对应的数据根本不在服务器 2 上**
- 服务器 2 只能当成"新用户"，要求重新登录
- 用户体感就是：**刚登录完，下一页就被踢出去**

### 根本原因

**Session 是"有状态"的**——状态存在某一台机器的内存里，换机器就丢。

## 四、业界怎么补救（都是额外成本）

| 方案 | 做法 | 问题 |
|---|---|---|
| **Session 复制** | 每次创建 Session 就广播同步给所有机器 | 网络开销大，机器越多越慢 |
| **粘性会话** | 让同一个 JSESSIONID 永远打到同一台机器 | 那台机器挂了，用户全掉线 |
| **集中存储** | Session 统一存 Redis（Spring Session） | 要额外引入 Redis，架构变重 |

- 这三种都是"打补丁"，**没有一个能像令牌那样天然免疫**
- 结论：**前后端分离 + 集群的项目，Session 不是好选择**

## 五、Session 常用 API（实战必备）

    // 获取 Session（没有就创建）
    HttpSession session = request.getSession();

    // 只获取，没有则返回 null（不想凭空创建时用）
    HttpSession session = request.getSession(false);

    // 存数据
    session.setAttribute("loginUser", "songjiang");

    // 取数据
    String user = (String) session.getAttribute("loginUser");

    // 删一条
    session.removeAttribute("loginUser");

    // 销毁整个会话（退出登录用）
    session.invalidate();

- **`getSession()` 无参版会自动创建**，所以别在拦截器里随便调它，否则每个匿名请求都会生成一个空 Session，把内存撑爆
- Session 也有超时时间（默认 30 分钟），到期自动销毁

## 六、三种方案的位置对照

| | Cookie | **Session** | JWT 令牌 |
|---|---|---|---|
| 数据存哪 | 浏览器 | 服务器内存 | 客户端（token 字符串） |
| 服务器有无状态 | 无 | **有**（要存 Session） | **无** |
| 集群友好 | ⚠️ | ❌ | ✅ |
| 用户能否篡改 | ✅ 能 | ❌ 不能 | ❌ 改了就验签失败 |
| 移动端可用 | ❌ | ❌（依赖 Cookie） | ✅ |
| 主动失效 | —— | ✅ `invalidate()` | ❌ 需配黑名单 |

## 七、易错点

| 问题 | 后果 |
|---|---|
| 以为 Session 不依赖 Cookie | **依赖**，JSESSIONID 就是通过 Cookie 传的，Cookie 一废 Session 也废 |
| 单机测试正常，上线集群后用户反复掉线 | 就是这页讲的集群问题 |
| 拦截器里直接 `request.getSession()` | 会**给每个匿名请求都创建 Session**，内存爆掉 |
| 把大对象（几 MB 的 List）塞进 Session | 内存压力大，用户一多就 OOM |
| 以为关了浏览器 Session 就没了 | 不一定，Session 存活由**服务器超时时间**决定 |
| 退出登录只删了前端数据 | 服务器 Session 还在，别人拿到 JSESSIONID 依然能用，要 `invalidate()` |
| 前后端分离还坚持用 Session | 端口不同就跨域，JSESSIONID 传不过去，得配 CORS + withCredentials，很别扭 |
| 用 `getSession(false)` 却忘了判 null | NPE |

## 八、口诀

> **Session = 数据存服务器内存 + 只把 JSESSIONID 通过 Cookie 交给浏览器**
> **优点：数据在服务端，用户改不了，安全**
> **缺点：集群不共享 + Cookie 的缺点它全继承**
> **集群下一台登录、另一台不认，用户被反复踢下线**
> **补救靠 Session 复制 / 粘性会话 / Redis 集中存储，全是额外成本**

# 会话跟踪方案（三）：令牌（JWT）—— 主流方案

## 一、先看图在讲什么（页面上的流程）

    浏览器(Chrome)  ── 请求（携带 token）──▶  统一拦截  ──▶  Login / Emp / Dept / Report
    浏览器(Chrome)  ◀── 响应（JSON）─────────  统一拦截  ◀──

  · 左边是浏览器（图上画了 Chrome）
  · 中间那根黄色竖条就是「统一拦截」——**所有请求先过拦截器**，不是每个接口自己校验
  · 右边四个深色模块 = 被保护的 Controller：Login、Emp、Dept、Report
  · 图下方大字「主流方案」，图上直接写了结论

## 二、图上列出的优缺点（原文照搬）

    优点：
    · 支持PC端、移动端
    · 解决集群环境下的认证问题
    · 减轻服务器端存储压力

    缺点：
    · 需要自己实现

  → 换句话说：**Session 的问题它一次全解决，代价是要自己写签发、校验、拦截**

## 三、为什么这三条是优点（对上 Session 的死穴）

| 对比维度 | Cookie | Session | 令牌 JWT |
| --- | --- | --- | --- |
| 数据存在哪 | 浏览器本地 | **服务器内存** | 不存在服务器，**存在令牌本身里** |
| 每次传什么 | 一堆业务数据 | 只传 JSESSIONID | 一长串 token（Base64 + 签名） |
| 依赖 Cookie？ | 是 | 是（JSESSIONID 靠 Cookie 传） | **不依赖**，放请求头就行 |
| 移动端 / APP | 不支持 | 不支持 | ✓ 支持（图上第 1 条优点） |
| 集群部署 | — | **多台不共享，换机器就掉线** | ✓ 服务器无状态，谁验都行（第 2 条） |
| 服务器存储压力 | — | 每人在内存里占一份 | ✓ 服务器不存（第 3 条） |
| 能否主动失效 | — | 能（session.removeAttribute） | **不能**，只能等过期 |
| 安全性 | 明文可篡改 | 较安全 | 签名防篡改，但 body 只是 Base64 可解码 |
| 实现成本 | 容器自带 | 容器自带 | **要自己实现**（图上唯一缺点） |

  · 「减轻服务器端存储压力」= Session 是**在服务器内存里给每个人开一个抽屉**，10 万在线就 10 万份；JWT 是**把数据写给用户自己保管，服务器只验签名**
  · 「解决集群」= 因为服务器什么都不存，所以**不依赖"上次是哪台机器"**&#8203;

## 四、JWT 结构（三段的由来）

    xxxxx.yyyyy.zzzzz
      │      │      └── 签名 Signature：HMAC-SHA256(header + payload, 密钥)
      │      └───────── 载荷 Payload：业务数据 + 过期时间 exp（Base64，可解码！）
      └──────────────── 头部 Header：{"alg":"HS256","typ":"JWT"}

  关键理解：
  · 前两段是**明文 Base64**，任何人都能解 → **绝不放密码、手机号等敏感信息**
  · 第三段签名保证「内容改一个字，验签就失败」
  · 服务器**不需要存令牌**，靠密钥重算签名比对 → 这就是「无状态」


## 五、易错点（按踩坑概率排序）

| 坑 | 后果 / 现象 |
| --- | --- |
| 拦截器没排除 `/login` | 登录接口也被拦 → **永远登不上**（401） |
| 返回 Emp 整体对象 | password 明文回到浏览器，安全漏洞 |
| 改了 payload 还想蒙过去 | 验签失败抛 SignatureException，正常现象 |
| 密钥（signKey）太短 | 0.11+ 抛 WeakKeyException，HS256 要求 ≥ 256bit(32 字节) |
| 服务端每次 new 新密钥 | 重启/多实例后旧 token 全部验不过 → 密钥必须**固定且全局一致** |
| 忘记 setExpiration | 令牌永不过期，被盗用后无法自愈 |
| 令牌前带 `Bearer ` 没处理 | 解析时把 "Bearer " 当令牌头 → 解码失败 |
| 前端只登录存 token，请求没带 | 登录成功但后续全 401（最常见的前端问题） |


## 六、三方案一句话总纲

    Cookie   —— 数据放浏览器，安全差、跨域废、APP 用不了
    Session  —— 数据放服务器内存，安全但集群不共享、占内存
    令牌 JWT —— 数据自己背着走，服务器只验签名
                ⇒ 跨域/集群/移动端全通，代价是「需要自己实现」

## 七、口诀

    请求发令牌，服务端验签；数据不落地，集群随便摆。
    缺点就一句：全得自己写（签发·校验·拦）。
    令牌不回收，过期要设短；密码别入 body，一解就露馅。
