# 修改员工（一）· 查询回显

## 一、为什么修改功能的第一步是"查"

点击列表里的「编辑」按钮，弹窗里要**把该员工现有的数据全部填好**，用户只改想改的字段。

这个"先把数据填进去"的过程就叫**回显**。

- 不回显 → 用户得从头重填所有字段，等于新增
- 所以修改 = **查询回显 + 提交修改**，两个接口，先查后改
- 这一页讲的是前者：`GET /emps/{id}`

## 二、表单里两块内容，来自两张表

| 页面区域 | 字段 | 表 |
|---|---|---|
| **上半：员工基本信息** | 用户名、姓名、性别、手机号、职位、薪资、所属部门、入职日期、头像 | `emp`（1 条） |
| **下半：员工工作经历** | 时间（起止）、公司、职位 | `emp_expr`（**多条**） |

- 这就是新增员工时的同一套结构，反过来了：**新增是"拆开写两张表"，修改是"合起来读两张表"**&#8203;
- 工作经历那几行右边还有个"删除"按钮，说明**修改时可能增删经历**，不只是改

## 三、三层职责（图下半部分）

| 层 | 职责 |
|---|---|
| **Controller** | ① 接收请求参数（**ID 值**）② 调用 Service 方法 ③ 响应结果 |
| **Service** | ① 调用 mapper 查询员工详细信息（**基本信息 + 工作经历信息**） |
| **Mapper** | 一条 SQL：`select ... from emp e left join emp_expr ee on e.id = ee.emp_id where e.id = ?` |

- Controller 只收一个 id（`@PathVariable`，接口是 `GET /emps/{id}`）
- Service 返回 `Emp` 对象（里面已经含 `exprList`）
- 注意：Service 这里**只查，不用事务**（单表查询不同步问题）

## 四、Mapper 的 SQL 逐句看

    select ...
    from emp e
    left join emp_expr ee on e.id = ee.emp_id
    where e.id = ?

| 片段 | 含义 |
|---|---|
| `from emp e` | 主表是员工 |
| `left join emp_expr ee` | 左外连接工作经历表，**没有经历的员工也要保留** |
| `on e.id = ee.emp_id` | 关联条件：员工 id = 经历表的 emp_id（一对多的外键） |
| `where e.id = ?` | 只查指定 id 的那个员工 |

### 为什么必须是 left join 而不是 inner join

- `inner join`：员工没有工作经历 → **一行都查不出来** → 页面空白
- `left join`：员工一定在结果里，没有经历时 expr 的字段为 null

> 这是关联查询的通用规律：**"查主体 + 附带明细"时永远用 left join。**&#8203;

## 五、⭐ 核心难点：一对多查出来是多行

一条员工记录 + 三条工作经历，join 之后是 **3 行**：

| e.id | e.name | ee.company |
|---|---|---|
| 1 | 张三 | 百度 |
| 1 | 张三 | 阿里 |
| 1 | 张三 | 腾讯 |

**员工字段重复了三遍。**&#8203; 如果直接 `List<Emp> list()`，你会得到 **3 个张三**，每个只有一条经历。

### 解决：resultMap + collection

    <resultMap id="empResultMap" type="com.itheima.pojo.Emp">
        <!-- 主键：MyBatis 靠它判断哪些行属于同一个员工 -->
        <id column="id" property="id"/>
        <result column="username" property="username"/>
        <result column="name" property="name"/>
        <result column="gender" property="gender"/>
        <result column="phone" property="phone"/>
        <result column="job" property="job"/>
        <result column="salary" property="salary"/>
        <result column="image" property="image"/>
        <result column="entry_date" property="entryDate"/>
        <result column="dept_id" property="deptId"/>
        <result column="create_time" property="createTime"/>
        <result column="update_time" property="updateTime"/>

        <!-- 一对多：把多行的经历收进 exprList -->
        <collection property="exprList" ofType="com.itheima.pojo.EmpExpr">
            <id column="expr_id" property="id"/>
            <result column="expr_emp_id" property="empId"/>
            <result column="expr_begin" property="begin"/>
            <result column="expr_end" property="end"/>
            <result column="expr_company" property="company"/>
            <result column="expr_job" property="job"/>
        </collection>
    </resultMap>

### 三个关键标签

| 标签 | 作用 |
|---|---|
| `<id>` | **主键映射**，MyBatis 用它判断"这几行是不是同一个人"，是合并的依据 |
| `<collection property="exprList" ofType="EmpExpr">` | 声明这是一对多集合：`property` 填 Emp 里的属性名，`ofType` 填**集合元素类型** |
| `<result>` | 普通字段映射，`column` 是 SQL 列名，`property` 是 Java 属性名 |

> 对比一对一的 `<association>`：一对多写 `<collection>`（集合），一对一写 `<association>`（单个对象）。

## 六、⚠️ 列名冲突必须处理

`emp` 和 `emp_expr` 都有 `id`、`create_time`、`update_time` 这些同名列。

如果 SQL 写成 `select e.*, ee.*` → 后面覆盖前面，员工的 `id` 会变成经历的 `id`，映射全错。

### 正确写法：给 expr 的列全部起别名

    <select id="getById" resultMap="empResultMap">
        select e.*,
               ee.id      as expr_id,
               ee.emp_id  as expr_emp_id,
               ee.begin   as expr_begin,
               ee.end     as expr_end,
               ee.company as expr_company,
               ee.job     as expr_job
        from emp e
        left join emp_expr ee on e.id = ee.emp_id
        where e.id = #{id}
    </select>

- 别名要和 `resultMap` 里 `<collection>` 的 `column` **一一对应**
- `begin` / `end` 是 MySQL 保留字 → 建表时就建议用反引号，查询时也建议 `` ee.`begin` ``

## 七、另一种更简单的做法（备选）

不 join，查两次：

| 步骤 | SQL |
|---|---|
| ① 查员工 | `select * from emp where id = ?` |
| ② 查经历 | `select * from emp_expr where emp_id = ?` |

然后在 Service 里 `emp.setExprList(list)` 拼起来。

| | 一次 join + resultMap | 两次查询 |
|---|---|---|
| 数据库往返 | 1 次 | 2 次 |
| 代码复杂度 | 高（要写 resultMap） | 低 |
| 适合 | 关联数据量大、要求性能 | 逻辑简单、教学理解 |

- 本项目课件用的是 join + resultMap，**企业里也更常用一次查询**

## 八、易错点

| 问题 | 后果 |
|---|---|
| 用 `inner join` | 没有工作经历的员工查不出来，页面空白 |
| 忘了写 `<id>` 标签 | 无法合并，返回 3 个重复的 Emp |
| `<collection>` 写了 `javaType` 而不是 `ofType` | 报类型不匹配 |
| `property` 写错（如 `exprlist`） | 集合收不到数据，exprList 为 null |
| SQL 用 `e.*, ee.*` 不起别名 | 列名覆盖，员工字段被经历的 id/time 覆盖 |
| 别名和 `<collection>` 的 column 不一致 | 经历字段全 null |
| `<select>` 用了 `resultType` 而不是 `resultMap` | 集合映射不生效，只映射到第一行 |
| Service 忘了返回 Emp 而是返回 List | Controller 拿到的结构不对，前端解析失败 |

## 九、口诀

> **修改 = 先查回显，再提交保存**
> **查主体带明细 → 必须 left join**
> **join 出来多行重复 → 用 resultMap + collection，靠 `<id>` 合并**
> **一对多用 collection（ofType），一对一用 association（javaType）**&#8203;
> **两张表同名列一定要起别名，否则互相覆盖**

# 思考题：XML文件中选resultType 还是 resultMap

## 一、课件原文的答案

> 1. Mybatis 中封装查询结果，什么时候用 resultType，什么时候用 resultMap？
> - 如果查询返回的**字段名与实体的属性名可以直接对应上**，用 **resultType**。
> - 如果查询返回的**字段名与实体的属性名对应不上，或实体属性比较复杂**，可以通过 **resultMap** 手动封装。

两句话的核心词就两个： **“能对上”** &#8203; 和  **“属性复杂”** &#8203;。

## 二、什么情况算"能直接对应上"

只要落在这三种里，都算能对上，用 `resultType` 就行：

| 情况 | 例子 | 说明 |
|---|---|---|
| ① 列名 = 属性名 | `name` ↔ `name` | 完全相同，直接映射 |
| ② 开了驼峰映射 | `entry_date` ↔ `entryDate` | 前提是 yml 配了 `map-underscore-to-camel-case: true` |
| ③ SQL 里起了别名 | `d.name deptName` ↔ `deptName` | 别名对上属性名，也算能对上 |

**写法：**

    <select id="getById" resultType="com.itheima.pojo.Emp">
        select * from emp where id = #{id}
    </select>

- 一行 `resultType` 搞定，不用手写任何字段映射
- 本项目之前的部门查询、员工分页查询，全是这种

## 三、什么情况算"对不上 / 属性复杂"

| 情况 | 举例 | 为什么 resultType 不行 |
|---|---|---|
| ① 名字毫无关系 | `select name as xx` 要映射到 `username` | 自动映射对不上，值变 null |
| ② **多表重名列** | `emp.id` 和 `emp_expr.id` 都要映射 | 两个同名 `id` 列，无法区分映射给谁 |
| ③ **实体含嵌套对象** | Emp 里有一个 `Dept dept` 属性 | 需要 `<association>` 声明一对一 |
| ④ **实体含集合** | Emp 里有 `List<EmpExpr> exprList` | 需要 `<collection>` 声明一对多 |

**写法：**

    <select id="getById" resultMap="empResultMap">
        select e.*, ee.id as expr_id, ee.company as expr_company
        from emp e left join emp_expr ee on e.id = ee.emp_id
        where e.id = #{id}
    </select>

- 必须配一个 `<resultMap>`，把每个列和属性手动对上

## 四、两者对照

| | `resultType` | `resultMap` |
|---|---|---|
| 使用前提 | 列名能和属性名对上 | 对不上，或结构复杂 |
| 是否要写映射 | 不用，自动 | **每个字段手写** |
| 能否处理嵌套对象 | ❌ | ✅ `<association>` |
| 能否处理集合 | ❌ | ✅ `<collection>` |
| 能否处理重名列 | ❌（会覆盖） | ✅（起别名 + column 对应） |
| 代码量 | 一行 | 一大段 |
| 适合 | 单表、扁平结构 | 多表关联、一对多/一对一 |

## 五、三条注意

- **只能二选一**：同一个 `<select>` 里不能既写 `resultType` 又写 `resultMap`
- **用 `resultMap` 时就不再写 `resultType`**，只写 `resultMap="映射的id"`
- **`resultMap` 里的 `<id>` 标签别省**：MyBatis 靠它判断"多行是否同一对象"（合并一对多时必须），顺带还能提高性能

## 六、判断流程（一秒钟决定）

    SQL 查出来的列 → 直接能填进实体属性吗？
        ├─ 能（名字一样 / 驼峰 / 别名对上了）→ resultType
        └─ 不能（名字不一致 / 有重名列 / 有嵌套对象或集合）→ resultMap

## 七、口诀

> **能对上就用 resultType，对不上或结构复杂就用 resultMap**
> **单表扁平 → resultType；多表嵌套、一对多 → resultMap**
> **重名列靠别名配 resultMap，集合靠 collection，对象靠 association**
> **两个只能写一个**

# 员工管理 - 修改员工（二）· 更新信息

## 一、页面长什么样（图上半部分）

点列表里的「编辑」按钮弹出「修改员工」弹窗，字段和新增员工**完全一样**：

| 区域 | 字段 |
|---|---|
| **基本信息**（对应 emp 表，1 条） | 用户名 username、姓名 name、性别 gender、手机号 phone、职位 job、薪资 salary、所属部门 deptId、入职日期 entrydate、头像 image |
| **工作经历**（对应 emp_expr 表，多条） | 时间（起止）、公司、职位 |

工作经历区域有两个按钮，这是理解本节的关键：

- 每行右侧的「**删除**」→ 用户可以删掉某条经历
- 右下角「**+ 添加工作经历**」→ 用户可以新增一条经历

所以用户点「保存」时，工作经历可能：**改了几条、删了几条、又加了几条**，任意组合。

- 图上「头像」下方提示：图片大小不超过 2M，仅能上传 PNG、JPEG、JPG 图片 → 复用之前写的 `/upload` 接口，`image` 字段存的是 URL

## 二、三层职责（图下半部分，原文）

| 层 | 职责 |
|---|---|
| **Controller** | ① 接收请求参数 ② 调用 Service 方法 ③ 响应结果 |
| **Service** | ① 根据 ID 修改员工的基本信息 ② 根据 ID 修改工作经历信息（**先删除再添加**） |
| **Mapper** | 三条 SQL：① `update emp set ...` ② `delete emp_expr where ...` ③ `insert into emp_expr ...` |

### 和新增员工的对比（重要）

| | 新增员工 | 修改员工 |
|---|---|---|
| 第 1 步 | `insert into emp` | **`update emp set ...`**（按 id 改） |
| 第 2 步 | `insert into emp_expr`（直接批量插） | **`delete from emp_expr where emp_id = ?`**（先删光） |
| 第 3 步 | —— | **`insert into emp_expr`**（再批量插） |

- 修改比新增**多了一条 delete**，这就是课件里 Service 那句「**先删除再添加**」的含义
- 请求方式也不同：新增 `POST /emps`，修改 `PUT /emps`（REST 规范：PUT 表示修改）

## 三、为什么是「先删除再添加」

### 如果不用全量覆盖，会怎样

假设某员工原来有 3 条经历，用户改完还是 3 条（其中 1 条改过、1 条删了、1 条新增），后端要做：

| 要做的判断 | 复杂度 |
|---|---|
| 哪些是**修改**的 → 要 update，得知道原 id | 高 |
| 哪些是**删除**的 → 要 delete，得知道原 id | 高 |
| 哪些是**新增**的 → 要 insert | 中 |

问题在于：前端传来的时，这三类数据没有明确区分（都是同一个 `exprList` 数组），后端得先查一遍原数据，再逐条比对。**逻辑又长又容易漏。**&#8203;

### 全量覆盖的做法

    -- ① 先把这员工的所有经历删干净
    delete from emp_expr where emp_id = 7;

    -- ② 把表单里的经历全部重新插进去
    insert into emp_expr(emp_id, begin, end, company, job) values (7,...),(7,...),(7,...);

- **不管前端改了几条、删了几条、加了几条，后端只做两件事**：删光、重插
- 代码就两行 Mapper 调用，没有比对逻辑
- 删和插在**同一个事务**里，中间不会有"经历不见了"的瞬间

### 代价（要清楚）

| 代价 | 说明 |
|---|---|
| 经历的主键全变 | 原来 id=11/12/13，重插后变成 14/15/16 |
| 不能拿经历 id 做外部关联 | 如果别的表引用了 emp_expr.id，这套策略就不能用 |
| 数据"看起来"被替换 | 虽然内容一样，但对数据库来说是新记录 |

> 本项目没有别的表引用 emp_expr.id，所以全量覆盖是最合适的做法。

两个要点：

| **exprList 里也带了 id** | 但用「全量覆盖」策略时，这些 id **用不上**（删光重插，id 由数据库重新生成） |

- 因为请求体结构和新增加载一样，还是用 `@RequestBody Emp` 接收，Emp 里已有 `exprList` 属性

## 五、三层代码骨架（先有个框架感）

### EmpController

    @PutMapping
    public Result update(@RequestBody Emp emp) {
        log.info("修改员工：{}", emp);
        empService.update(emp);
        return Result.success();
    }

### EmpServiceImpl

    @Transactional(rollbackFor = Exception.class)
    @Override
    public void update(Emp emp) {
        // 1. 补全属性（只补 updateTime，createTime 不能改）
        emp.setUpdateTime(LocalDateTime.now());

        // 2. 修改员工基本信息
        empMapper.update(emp);

        // 3. 全量覆盖工作经历：先全删
        empExprMapper.deleteByEmpIds(Collections.singletonList(emp.getId()));

        // 4. 再全量插入（注意要设 empId）
        if (emp.getExprList() != null && !emp.getExprList().isEmpty()) {
            emp.getExprList().forEach(expr -> expr.setEmpId(emp.getId()));
            empExprMapper.insertBatch(emp.getExprList());
        }
    }

### Mapper 三条 SQL

    <!-- ① 修改员工基本信息 -->
    update emp set username = #{username}, name = #{name}, gender = #{gender},
                   phone = #{phone}, job = #{job}, salary = #{salary},
                   image = #{image}, entry_date = #{entryDate}, dept_id = #{deptId},
                   update_time = #{updateTime}
    where id = #{id}

    <!-- ② 删除该员工的工作经历 -->
    delete from emp_expr where emp_id in (?, ?, ?)

    <!-- ③ 批量插入工作经历 -->
    insert into emp_expr(emp_id, begin, end, company, job) values (?,?,?,?,?), (?,?,?,?,?)

- 第 ②③ 两条直接复用**新增员工那节写好的** `deleteByEmpIds` 和 `insertBatch`，一行都不用改
- 只有第 ① 条 `update` 是本节新写的

## 六、易错点（本节先埋坑，后面代码课会踩）

| 问题 | 后果 |
|---|---|
| `update` 语句**漏写 `where id = ?`** | **全表所有员工被改成同一个人** —— 最惨烈的事故 |
| 补了 `createTime` | 创建时间被改成当前时间，数据失真（修改只能动 updateTime） |
| 先删后插时**忘了给每条 expr 设 empId** | 插入的记录 emp_id 为 null，经历挂不上任何人 |
| `exprList` 为空还去插 | `values` 后面是空的 → SQL 语法错误，必须先判空 |
| `deleteByEmpIds` 形参是 `List`，却传了单个 `emp.getId()` | 类型不匹配，编译不过，要包成集合 |
| 三条 SQL 没有同一个事务 | 删完插入失败 → 经历全丢，比不改还糟 |
| 固定写法 update 全部字段 | 若前端只传部分字段，没传的字段会被刷成 **null**（下一节大概率讲 `<set>` + `<if>` 按需更新） |
| Controller 用 `@PostMapping` | 修改按 REST 规范用 `PUT`，路径冲突且语义错 |

⚠️ 关于"字段被刷成 null"再强调一句：`update emp set salary = #{salary} where id = ?`，如果请求里没带 salary，那 salary 就被写成 null 了。真实项目里修改接口要么前端传全量，要么后端用动态 SQL（`<set>` + `<if test="salary != null">`）只改非空字段。

## 七、口诀

> **修改 = 回显（查）+ 提交（改），两个接口**
> **改人一条 update，改经历先删后插**
> **全量覆盖：删光再重插，不用比对增删改**
> **update 千万别漏 where id，事务一定要加**
