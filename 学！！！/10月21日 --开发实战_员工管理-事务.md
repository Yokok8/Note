# 事务（Transaction）

## 一、为什么需要事务

接着上一节的新增员工：一次操作要插**两张表**。

    -- 1. 保存员工基本信息
    insert into emp values (39, 'Tom', '123456', '汤姆', 1, '13300001111', 1, 4000, '1.jpg', '2023-11-01', 1, now(), now());

    -- 2. 保存员工的工作经历信息
    insert into emp_expr(emp_id, begin, end, company, job) values (39,'2019-01-01','2020-01-01','百度','开发'),
                                                                  (39,'2020-01-10','2022-02-01','阿里','架构');

问题来了：如果第 1 条成功了、第 2 条失败了会怎样？

| 结果 | 数据状态 |
|---|---|
| 只有 emp 成功 | 表里有个员工，但一条工作经历都没有 → **数据不完整** |
| 只有 emp_expr 成功 | 经历挂在一个不存在的员工上 → **脏数据** |

**这就是事务要解决的问题。**&#8203;

## 二、什么是事务（概念原文）

> **事务是一组操作的集合，它是一个不可分割的工作单位。事务会把所有的操作作为一个整体一起向系统提交或撤销操作请求，即这些操作要么同时成功，要么同时失败。**&#8203;

拆开看三个关键词：

| 关键词 | 含义 |
|---|---|
| **一组操作的集合** | 事务里可以有多条 SQL（本例 2 条） |
| **不可分割的工作单位** | 要么整体算数，要么整体不算 |
| **同时成功 / 同时失败** | 不存在"成功一半"的中间状态 |

## 三、⚠️ 前提：MySQL 默认是自动提交的

> **默认 MySQL 的事务是自动提交的，也就是说，当执行一条 DML 语句，MySQL 会立即隐式地提交事务。**&#8203;

- `insert` / `update` / `delete` 每执行一条，就会**立刻生效**，没法反悔
- 所以想用事务，必须**显式开启**

## 四、事务控制三步操作

| 步骤 | 命令 | 作用 |
|---|---|---|
| ① 开启事务 | `start transaction;` 或 `begin;` | 从这里开始，后面的 SQL 进入同一事务 |
| ② 提交事务 | `commit;` | **全部成功**时才执行，数据真正落库 |
| ③ 回滚事务 | `rollback;` | **只要有一项失败**就执行，撤销事务内所有操作 |

- `start transaction` 和 `begin` 是**同义词**，写哪个都行

## 五、完整演示（把上一步的 SQL 包进事务）

    -- 开启事务
    start transaction;        -- 或 begin;

    -- 1. 保存员工基本信息
    insert into emp values (39, 'Tom', '123456', '汤姆', 1, '13300001111', 1, 4000, '1.jpg', '2023-11-01', 1, now(), now());

    -- 2. 保存员工的工作经历信息
    insert into emp_expr(emp_id, begin, end, company, job) values (39,'2019-01-01','2020-01-01','百度','开发'),
                                                                  (39,'2020-01-10','2022-02-01','阿里','架构');

    -- 提交事务（全部成功） / 回滚事务（有一个失败）
    commit;                   -- 或 rollback;

### 两条结局

| 情况 | 执行 | 结果 |
|---|---|---|
| 两条 insert 都成功 | `commit;` | 员工 + 经历一起入库 |
| 第二条 insert 失败 | `rollback;` | **第一条也被撤销**，数据库回到事务开始前的样子 |

## 六、思考题（课件最后一页）

### 1. 什么是事务？

- 事务是一组操作的集合，是一个不可分割的工作单位。这组操作**要么全部成功，要么全部失败**。

### 2. 如何控制事务？

| 操作 | 命令 | 时机 |
|---|---|---|
| 开启事务 | `start transaction` / `begin;` | 在执行 DML 之前 |
| 提交事务 | `commit;` | **全部成功** |
| 回滚事务 | `rollback;` | **只要有一项失败** |

### 3. 应用场景有哪些？

- **银行转账**：A 扣钱、B 加钱，只能一起成功
- **下单扣减库存**：订单生成 + 库存减少，不能只做一半
- **本项目**：新增员工要写 emp 和 emp_expr 两张表

## 七、易错点

| 问题 | 说明 |
|---|---|
| 以为 MySQL 会自动开事务 | 默认是**自动提交**，不显式开启就没有事务保护 |
| 开了事务忘了 commit | 连接关闭时可能回滚，数据白插 |
| 在事务里执行 DDL（如 create table） | DDL 会隐式提交，破坏事务边界 |
| 只关心"成功路径"不写回滚 | 实际出错时数据已经半截入库 |
| 把事务开在 Controller 层 | 规范做法是在 Service 层，一个业务方法一个事务 |

## 八、口诀

> **事务 = 一组操作的整体，要么全成、要么全败**
> **MySQL 默认自动提交，所以要手动 start transaction**
> **成功 commit，失败 rollback，Java 里一个 @Transactional 搞定**

# Spring 事务管理 - 控制事务（@Transactional）

## 一、三要素（课件原文）

| 项 | 内容 |
|---|---|
| **注解** | `@Transactional` |
| **作用** | 将当前方法交给 Spring 进行事务管理，**方法执行前开启事务；成功执行完毕提交事务；出现异常回滚事务** |
| **位置** | 业务（service）层的**方法上、类上、接口上** |

上一节在 SQL 里手写 `start transaction / commit / rollback`，Java 里一个注解全包了。

## 二、注解背后的生命周期

    @Transactional
    public void save(Emp emp) { ... }

    ┌─ 方法执行前 ──→ Spring 自动开启事务
    │
    ├─ 方法正常执行完 ──→ 自动 commit（提交）
    │
    └─ 方法抛异常 ──→ 自动 rollback（回滚）

- 全程**不需要你写任何事务代码**，开关交给 Spring

## 三、三个位置怎么选

| 位置 | 生效范围 | 适用场景 |
|---|---|---|
| **方法上**（推荐 ✅） | 只作用这一个方法 | 只有个别方法需要事务 |
| **类上** | 该类的**所有 public 方法** | 整个 Service 都要事务（少见） |
| **接口上** | 实现了该接口的类的**所有方法** | 能生效但不推荐，耦合重 |

> 课件把方法上标为**推荐**，因为最精准——只给需要事务的方法加，不影响其他查询方法。

## 四、三种写法（完整）

### ① 方法上（推荐）

    @Transactional
    @Override
    public void save(Emp emp) {
        // 1. 补全基础属性
        emp.setCreateTime(LocalDateTime.now());
        emp.setUpdateTime(LocalDateTime.now());

        // 2. 保存员工基本信息
        empMapper.insert(emp);

        int i = 1 / 0;      // ★ 故意制造异常，用来验证事务回滚

        // 3. 保存员工的工作经历信息 - 批量
        Integer empId = emp.getId();
        List<EmpExpr> exprList = emp.getId() ...;
    }

- `int i = 1 / 0;` 会抛 `ArithmeticException`（属于 RuntimeException）
- 加上这行后如果 emp 表没多出数据 → 说明回滚成功

### ② 类上

    @Transactional
    @Service
    public class EmpServiceImpl implements EmpService {
        // 这里所有 public 方法都带事务
    }

### ③ 接口上

    @Transactional
    public interface EmpService {
        // 实现类的所有方法都带事务
    }

## 五、怎么验证事务真的生效

### 配置底层日志（application.yml）

    # 配置日志信息，查看spring事务管理的底层日志
    logging:
      level:
        org.springframework.jdbc.support.JdbcTransactionManager: debug

- 打开后调用接口，控制台会打印事务的**创建 / 提交 / 回滚**过程
- 这就是上一节学 Logback 的实际用途：调别人的框架日志

### 日志类名要注意版本

| SpringBoot 版本 | 事务管理器类名 |
|---|---|
| 3.x（Spring 6） | `org.springframework.jdbc.support.JdbcTransactionManager` |
| 2.x | `org.springframework.jdbc.datasource.DataSourceTransactionManager` |

- 配错了不会报错，只是**日志打不出来**，容易误以为事务没生效

### 验证步骤

1. 打开 debug 日志
2. 调 `POST /emps` 新增员工
3. 看控制台：出现 `rolling back` 之类的日志 + emp 表无新数据 → 回滚成功
4. 把 `int i = 1/0;` 删掉再测 → 数据正常入库

## 六、什么时候会回滚、什么时候不会

| 异常类型                                                         | 默认是否回滚      |
| ------------------------------------------------------------ | ----------- |
| RuntimeException（含 ArithmeticException、NullPointerException） | ✅ 回滚        |
| Error                                                        | ✅ 回滚        |
| 受检异常（Exception 中非 RuntimeException 的）                        | ❌ **默认不回滚** |

要让受检异常也回滚，得显式指定：

    @Transactional(rollbackFor = Exception.class)

- 实际项目建议**统一写上 `rollbackFor = Exception.class`**，避免踩坑

## 七、事务失效的常见场景

| 场景 | 原因 |
|---|---|
| 同类内部方法直接调用（this.xxx()） | 不走 Spring 代理，注解不生效 |
| 方法不是 public | Spring 代理拦截不到 |
| 异常被 try-catch 吞掉没抛出 | Spring 收不到异常，照常提交 |
| 类没被 Spring 管理（没加 @Service 等） | 没有代理对象 |
| 数据库引擎是 MyISAM | 不支持事务，只有 InnoDB 才支持 |
| 在事务方法里做了外部调用（发消息） | 外部操作不回滚，要考虑补偿 |

## 八、易错点

| 问题 | 后果 |
|---|---|
| 标注在 Controller 上 | 一般无效（Controller 不常被代理），且职责不对 |
| 只加了 `@Transactional` 忘了 import | 编译报错，注意是 `org.springframework.transaction.annotation.Transactional` |
| 以为日志没打就是没生效 | 多半是类名版本写错了 |
| 用受检异常测试回滚 | 不会回滚，误判为注解失效 |
| 把 `1/0` 留在正式代码里 | 上线必炸，测完删掉 |

## 九、口诀

> **`@Transactional` 三要素：方法前开、成功提交、异常回滚**
> **位置：方法上最推荐，类上次之，接口上少用**
> **验证靠 JdbcTransactionManager 的 debug 日志 + 一句 1/0**
> **受检异常默认不回滚，记得加 rollbackFor**

# 事务进阶 - rollbackFor

## 一、这个属性解决什么问题

上一页只写了 `@Transactional`，看起来已经很好了，但有个**默认陷阱**：

> **默认情况下，只有出现 RuntimeException 才会回滚。**&#8203;

也就是说，如果你的方法抛的是**受检异常**（如 `IOException`、`SQLException`、自定义的 `Exception` 子类），Spring 会**照常提交事务**，数据照样入库——白瞎了事务保护。

`rollbackFor` 就是用来把这个范围改大的。

## 二、语法

    @Transactional(rollbackFor = {Exception.class})

- `rollbackFor` 的值是 **Class 数组**，花括号 `{}` 是数组写法
- 只写一个类型时，`{}` 也可以省略：`@Transactional(rollbackFor = Exception.class)`，效果一样
- 需要多个时：

    @Transactional(rollbackFor = {IOException.class, SQLException.class})

## 三、默认 vs 指定后

| 异常类型 | 只用 `@Transactional` | 加 `rollbackFor = Exception.class` |
|---|---|---|
| RuntimeException（1/0、空指针） | ✅ 回滚 | ✅ 回滚 |
| Error | ✅ 回滚 | ✅ 回滚 |
| 受检异常（IOException 等） | ❌ **不回滚** | ✅ **回滚** |

- 关键点：`Exception.class` 是"所有能被业务代码 catch 的异常"的总父类，写它等于**兜底全包**

## 四、课件完整代码

    @Transactional(rollbackFor = {Exception.class})
    @Override
    public void save(Emp emp) {
        // 1. 保存员工基本信息
        emp.setCreateTime(LocalDateTime.now());
        emp.setUpdateTime(LocalDateTime.now());
        empMapper.insert(emp);

        // 2. 保存员工的工作经历信息
        // ... 省略
    }

- 只改了第一行，方法体一点不用动
- 这就是框架注解的方便之处：**换个参数就能改变行为**

## 五、实际项目建议

**所有需要事务的业务方法，统一这么写：**

    @Transactional(rollbackFor = Exception.class)

理由：

- 业务代码里经常有无从预料的受检异常（IO、SQL、第三方 SDK 抛的）
- 默认规则太隐蔽，出问题时排查很痛苦（数据半截入库但不报错）
- 统一加上不会带来副作用，只是把"该回滚的"都框进来

## 六、易错点

| 问题 | 说明 |
|---|---|
| 以为加了 `@Transactional` 就万事大吉 | 受检异常默认不回滚，这是最普遍的坑 |
| 写 `rollbackFor = RuntimeException.class` | 等于没写，跟默认一样 |
| 写 `rollbackFor = Throwable.class` | 能覆盖 Error，但一般没必要，`Exception` 足够 |
| 异常被 try-catch 吞了 | 不管 rollbackFor 配什么都不会回滚，因为 Spring 收不到 |
| 数组写法漏写 `.class` | 编译报错，要写 `IOException.class` 而非 `IOException` |

## 七、口诀

> **`rollbackFor` 管"什么异常回滚"，默认只认 RuntimeException**
> **受检异常默认不回滚，必须 `rollbackFor = Exception.class` 兜住**
> **统一加上，不用犹豫**

# 事务进阶 - propagation（事务传播行为）

## 一、什么是传播行为（定义原文）

> **事务传播行为：指的就是当一个事务方法被另一个事务方法调用时，这个事务方法应该如何进行事务控制。**&#8203;

场景长这样：

    @Transactional
    public void a() {
        // ...
        userService.b();   // ← a 有事务，b 也有事务，那 b 怎么办？
        // ...
    }

    @Transactional(propagation = Propagation.REQUIRED)
    public void b() {
        // ...
    }

核心问题只有一句：**内层方法 b 是"加入"外层 a 的事务，还是自己"新建"一个？**

## 二、属性值全表（课件原文）

| 属性值 | 含义 |
|---|---|
| **REQUIRED** | **【默认值】需要事务，有则加入，无则创建新事务** |
| **REQUIRES_NEW** | 需要新事务，无论有无，总是创建新事务 |
| SUPPORTS | 支持事务，有则加入，无则在无事务状态中运行 |
| NOT_SUPPORTED | 不支持事务，在无事务状态下运行；如果当前存在已有事务，则**挂起**当前事务 |
| MANDATORY | 必须有事务，否则抛异常 |
| NEVER | 必须没事务，否则抛异常 |
| …（还有 NESTED 等） | 课件省略 |

- 后四个（SUPPORTS / NOT_SUPPORTED / MANDATORY / NEVER）在业务开发中基本用不到，**理解 REQUIRED 和 REQUIRES_NEW 就够**

## 三、重点：REQUIRED vs REQUIRES_NEW

设一个场景：`a()` 里调用 `b()`，`b()` 执行完了，`a()` 后面抛异常。

| | REQUIRED（默认） | REQUIRES_NEW |
|---|---|---|
| b 的事务 | **加入** a 的事务，用的是同一个 | **挂起** a 的事务，自己**新开**一个 |
| a 抛异常时 | a、b **全部回滚** | 只回滚 a，**b 已提交的数据保留** |
| 事务数量 | 1 个 | 2 个 |
| 数据库连接 | 1 个 | **2 个**（外层被挂起但不释放） |

### 什么时候用 REQUIRES_NEW

**典型场景：不管主业务成不成功，都要留下记录。**&#8203;

    @Transactional(rollbackFor = Exception.class)
    public void createOrder(Order order) {
        orderMapper.insert(order);        // 主业务
        logService.saveLog("下单成功");    // 日志服务用 REQUIRES_NEW
        int i = 1 / 0;                    // 主业务后续失败
    }

- 用默认 REQUIRED：订单回滚，日志也一起回滚 → **日志白记了**
- 用 REQUIRES_NEW：订单回滚，**日志保留** → 才能查出"这次下单尝试发生了"

## 四、代码写法

    @Service
    public class UserServiceImpl implements UserService {

        @Transactional(rollbackFor = Exception.class)
        public void a() {
            // 业务逻辑
            userService.b();
        }

        @Transactional(propagation = Propagation.REQUIRES_NEW, rollbackFor = Exception.class)
        public void b() {
            // 独立事务，不受 a 回滚影响
        }
    }

- 默认不写 `propagation` 就等于 `Propagation.REQUIRED`
- 写全了就是 `@Transactional(propagation = Propagation.REQUIRED)`

## 五、易错点

| 问题 | 说明 |
|---|---|
| 以为两个方法各自 `@Transactional` 就互不影响 | 默认 REQUIRED 会**合并成一个事务**，一起回滚 |
| 用 REQUIRES_NEW 结果没生效 | 内层方法若是**同类自调用**（this.b()），不走代理，传播行为失效 |
| 嵌套太多 REQUIRES_NEW | 每层占一个连接，高并发下**连接池可能耗尽**，甚至死锁 |
| REQUIRES_NEW 里又调用 REQUIRED 方法 | 那个方法会加入 REQUIRES_NEW 的新事务，回滚边界要重新想清楚 |
| MANDATORY / NEVER 用错 | 直接抛 `IllegalTransactionStateException` |

## 六、实操建议

- **绝大多数情况：什么都不写，用默认 REQUIRED**
- 只有明确需要"内层独立提交、不被外层回滚影响"时，才用 REQUIRES_NEW（日志、审计、消息记录）
- 用 REQUIRES_NEW 前先想清楚：这个操作失败了能不能接受外层已经回滚？两边的数据一致性谁负责？

## 七、口诀

> **传播行为 = 内层事务方法遇上外层事务方法时怎么办**
> **REQUIRED 加入（默认，同生共死），REQUIRES_NEW 新建（各自独立）**&#8203;
> **要留痕不受回滚影响 → REQUIRES_NEW；其余一律默认**

# 事务四大特性（ACID）

## 一、四个特性（课件原文）

| 特性 | 英文 | 原文表述 |
|---|---|---|
| **原子性** | **A**tomicity | 事务是**不可分割的最小单元**，要么全部成功，要么全部失败 |
| **一致性** | **C**onsistency | 事务完成时，必须使所有的数据都保持**一致状态** |
| **隔离性** | **I**solation | 数据库系统提供的隔离机制，保证事务在**不受外部并发操作影响的独立环境下**运行 |
| **持久性** | **D**urability | 事务一旦提交或回滚，它对数据库中的数据的改变就是**永久的** |

四个大写字母连起来就是 **ACID**，这是事务的标准叫法。

## 二、用"银行转账"一例串起四个特性

场景：A 给 B 转 100 元，原本各 100，现在 A 扣 100、B 加 100。

| 特性 | 在这个场景里意味着什么 | 反例（不满足会怎样） |
|---|---|---|
| **原子性** | A 扣钱和 B 加钱**必须都成**，只做一半就撤销 | A 扣了钱，B 没收到 → 钱凭空消失 |
| **一致性** | 转账前后 A+B 总额都是 **200**，不能多不能少 | 总额变 100 或 300 → 数据非法 |
| **隔离性** | 转账进行中，别人查余额看到的**不是中间状态** | 别人看到"钱已扣但还没到账" → 误判 |
| **持久性** | 转账成功后立刻数据库宕机，重启后**结果还在** | 宕机后记录消失 → 用户钱没了 |

## 三、怎么快速记住

一句话版本：

| 特性 | 记法 |
|---|---|
| 原子性 | **全成功或全失败**（不可分割） |
| 一致性 | **数据始终合法**（从正确状态到正确状态） |
| 隔离性 | **并发不干扰**（各干各的） |
| 持久性 | **提交就不丢**（落盘） |

四个字概括：**全、正、独、稳**。

## 四、谁保证谁（扩展，面试常问）

| 特性 | 底层靠什么 |
|---|---|
| 原子性 | **undo log（回滚日志）**&#8203;：记录修改前的旧值，失败时按旧值撤销 |
| 隔离性 | **锁 + MVCC**：配合隔离级别控制并发访问 |
| 持久性 | **redo log（重做日志）**&#8203;：先写日志再写数据，宕机后可恢复 |
| 一致性 | **没有单独的机制**——它是原子性、隔离性、持久性共同作用的结果，再加上业务约束（外键、唯一索引等） |

- 记忆点：**一致性是目的，其他三个是手段**

## 五、和前面几节的关系

- 上一节的 `@Transactional` + `rollbackFor`：保证的是 **A（原子性）**&#8203;
- 这一节的 ACID 是**事务的理论基础**，`@Transactional` 只是 Spring 对这个理论的实现
- 隔离性往下延伸就是**数据库的隔离级别**（读未提交 / 读已提交 / 可重复读 / 串行化），以及脏读、不可重复读、幻读三个问题

## 六、易错点

| 问题 | 说明 |
|---|---|
| 把原子性理解成"SQL 次数少" | 原子性说的是**不可分割**，跟次数无关 |
| 以为一致性靠某个日志实现 | 一致性是**结果状态**，靠其他三个特性 + 约束共同保证 |
| 混淆隔离性和原子性 | 原子性管"这个事务内部的完整性"，隔离性管"事务之间的互不干扰" |
| 以为持久性靠"提交"这个动作 | 真正落地靠 **redo log 刷盘**，不是 commit 本身 |

## 七、口诀

> **A 全成功或全失败，C 数据始终合法**
> **I 并发互不干扰，D 提交永不丢失**
> **undo 保原子、锁和 MVCC 保隔离、redo 保持久，一致性是三者共同的结果**
