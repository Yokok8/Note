# 多表关系（概述）

## 一、为什么会有表关系（课件原文）
项目开发中，在进行**数据库表结构设计**时，会根据**业务需求及业务模块之间的关系**，分析并设计表结构。
由于业务之间相互关联，所以各个表结构之间也存在着各种联系。

一句话：**业务有联系 → 表就有联系**（比如"一个部门下有多个员工"，部门和员工表就产生了关系）。

## 二、三种关系（全部考点就这三种）
| 关系 | 经典例子 | 怎么实现 |
|---|---|---|
| **一对多（多对一）**&#8203; | 部门 ↔ 员工（一个部门多个员工） | **在"多"的一方加外键** |
| **一对一** | 用户 ↔ 用户详情（拆表存） | 任意一边加外键 |
| **多对多** | 学生 ↔ 课程（一个学生选多门课） | **需要中间表** |

## 三、口诀
- **业务有关联，表就有关系**
- **三种：一对多、一对一、多对多**
- **一对多靠外键（加在多的一方），多对多靠中间表**

# 一对多（多对一）

## 一、场景
**部门与员工的关系**：一个部门下有多个员工。

## 二、两张表长什么样（照图）

### 父表 dept（一的一方）
| id（主键） | name |
|---|---|
| 1 | 学工部 |
| 2 | 研发部 |
| 3 | 咨询部 |
| 4 | 就业部 |
| 5 | 人事部 |
| 6 | 行政部 |

### 子表 emp（多的一方）
| id | username | password | name | gender | phone | job | salary | **dept_id** |
|---|---|---|---|---|---|---|---|---|
| 1 | shinaian | 123456 | 施耐庵 | 1 | 13309090001 | 4 | 15000 | **2** |
| 2 | songjiang | 123456 | 宋江 | 2 | 13309090002 | 2 | 8600 | **2** |
| ... | ... | ... | ... | ... | ... | ... | ... | ... |
| 7 | chaijin | 123456 | 柴进 | 1 | 13309090007 | 1 | 4700 | **1** |
| 10 | lichong | 123456 | 林冲 | 1 | 13309090010 | 1 | 5000 | **1** |

关键：**emp 表最后多了一个 `dept_id` 字段**，而 dept 表里没有 emp 的任何字段。

## 三、⭐ 实现方式（课件红字，背下来）
**一对多的关系如何实现？**
> **在数据库中多的一方，添加字段，来关联一的一方的主键。**&#8203;

落地到这张图：
- 多的一方 = **emp** → 加字段 **dept_id**
- 一的一方 = **dept** → 被关联的是它的**主键 id**
- dept_id 这个字段就叫**外键**

## 四、怎么读这些数据
- emp 表里 dept_id = 2 的员工（施耐庵、宋江、卢俊义…）→ 都属**研发部**
- emp 表里 dept_id = 1 的员工（柴进、李逵、武松、林冲）→ 都属**学工部**
- **一个部门 id 被多个员工重复引用** → 这就是"一对多"的直观体现

## 五、易错点
| 易错                  | 说明                      |
| ------------------- | ----------------------- |
| 反过来在 dept 表加 emp_id | 错！部门只有一个，加在"一"方没法表示多个员工 |
| 把外键加在一的一方           | 一对多**只能加在多的一方**         |
| 分不清父表子表             | 一的一方是**父表**，多的一方是**子表** |
| 以为 dept_id 要唯一      | 不用唯一，**重复的值正是一对多的体现**   |

## 六、口诀
- **一对多加在多的一方，关联一的一方主键**
- **一的一方是父表，多的一方是子表**
- **外键值会重复，重复说明一对多**

# 多表问题分析

## 一、现象（课件原文）
部门数据**可以直接删除**，然而还有部分员工归属于该部门下，此时就出现了数据的**不完整、不一致**问题。

具体场景：
1. dept 表里有 id=1 的"学工部"
2. emp 表里有 4 个员工的 dept_id = 1（施耐庵、宋江…）
3. 执行 `delete from dept where id = 1` → **部门删掉了，员工还挂着 dept_id = 1**
4. 员工数据成了"**孤儿数据**"——找不到对应部门了

## 二、原因（课件原文）
目前上述的两张表，**在数据库层面，并未建立关联**，所以是无法保证数据的**一致性和完整性**的。

关键理解：`dept_id` 目前只是个**普通字段**，名字里带 dept 但数据库**根本不认识它和 dept 表有关系**。
→ 所以删部门时数据库**不会拦你**，也不会做任何处理。

## 三、解决方案
**外键约束**（FOREIGN KEY）

加了外键约束后，数据库就"知道"这两张表有关系了，于是：
- 想删除被引用的部门时，数据库会**直接拦住报错**
- 从根上保证数据的完整性和一致性

## 四、两个关键词（面试常问）
| 词 | 含义 |
|---|---|
| **完整性** | 数据该有的都得有，不能缺胳膊少腿（不能有指向不存在部门的员工） |
| **一致性** | 相关联的数据之间要对得上（emp.dept_id 必须能在 dept.id 里找到） |

## 五、易错点
| 易错 | 说明 |
|---|---|
| 以为字段名叫 dept_id 就是外键 | **名字像 ≠ 真的是外键**，必须显式加外键约束 |
| 以为业务代码里查得到就算有关联 | 数据库层面没约束，绕过代码直接删库照样出问题 |
| 认为外键只在删的时候有用 | 插入/更新也有用：插入一个不存在的 dept_id 同样会被拦 |
| 把"现象/原因/方案"顺序记反 | 现象=能删后又出问题；原因=没建关联；方案=外键约束 |

## 六、口诀
- **部门能直接删，员工却还挂着 → 数据不完整不一致**
- **原因就一句：数据库层面没建立关联**
- **解决方案：加外键约束**

# 外键约束的创建

## 一、两种添加时机（课件原文）
可以在**创建表时** 或 **表结构创建完成后**，为字段添加外键约束。

### 方式一：创建表时指定
    -- 创建表时指定
    create table 表名(
        字段名 数据类型,
        ...
        [constraint] [外键名称] foreign key (外键字段名) references 主表 (字段名)
    );

### 方式二：建完表后添加
    -- 建完表后，添加外键
    alter table 表名 add constraint 外键名称 foreign key (外键字段名) references 主表(字段名);

实际做项目时，**第二种更常用**（表已经建好了，回头补外键）。

## 二、语法要素拆解
拿 emp 加外键举例：
    alter table emp add constraint fk_emp_dept foreign key (dept_id) references dept(id);

| 部分 | 含义 |
|---|---|
| alter table emp | 要改**子表** emp |
| add constraint | 添加一个约束 |
| **fk_emp_dept** | **外键名称**，自己起（规范：fk_子表_主表） |
| foreign key (dept_id) | 本表哪个字段是外键 |
| references dept(id) | 关联到**主表 dept 的主键 id** |

记忆对应：**foreign key 写"多的一方"的字段，references 写"一的一方"的表和主键**。

## 三、⭐ 物理外键 vs 逻辑外键（重点结论）
### 物理外键
- **概念**：使用 `foreign key` 定义外键关联另外一张表
- **缺点（三条，要背）**&#8203;：
  1. 影响**增、删、改的效率**（每次都要检查外键关系）
  2. 仅用于**单节点数据库**，不适用**分布式、集群**场景
  3. 容易引发数据库的**死锁**问题，消耗性能

### 逻辑外键
- **概念**：在**业务层逻辑**中，解决外键关联
- **通过逻辑外键，就可以很方便地解决上述问题**

### 对比
| | 物理外键 | 逻辑外键 |
|---|---|---|
| 在哪实现 | 数据库（foreign key） | **业务层代码** |
| 性能 | 影响增删改效率 | 不影响 |
| 集群/分布式 | 不支持 | **支持** |
| 死锁风险 | 有 | 无 |
| 企业实际用法 | 基本不用 | **推荐** |

**一句话结论：数据库里不建物理外键，关联关系靠程序代码（Service 层）来保证。**&#8203;

## 四、易错点
| 易错 | 说明 |
|---|---|
| 以为必须建物理外键 | 企业开发大多**不建**，用逻辑外键 |
| 外键加错表 | 加在**多的一方（子表）**&#8203;，别加到父表上 |
| 外键名称随便起又重名 | 建议统一 `fk_子表_主表` 命名，避免冲突 |
| 已有脏数据时加外键 | 加不上，会报错（得先清理孤儿数据） |
| 把缺点记混 | 物理外键的三个缺点：慢、不支持集群、易死锁 |

## 五、口诀
- **加外键两种方式：建表时指定 / 建完表 alter 添加**
- **foreign key 写子表字段，references 写主表主键**
- **物理外键有条条框框，项目里用逻辑外键**
